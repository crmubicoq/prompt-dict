# devlog — 기술 기록

재사용 가치가 있는 원리·함정·패턴을 **주제별로** 축적한다. 날짜순 아님.
그날 무엇을 했는지는 [`worklog/`](./worklog/), 왜 그렇게 정했는지는 [`decisions/`](./decisions/).

## 1. 단일 HTML 분할

### 1.1 일반 `<script>` 는 전역 공간을 공유한다

ES 모듈이 아니면 `import`/`export` 가 없고, 여러 `<script>` 가 **하나의 전역 공간**을 쓴다.
그래서 함수를 어느 파일에 넣든 서로 호출된다.

### 1.2 ★ "호이스팅이라 순서 무관"은 틀린 설명

호이스팅은 **같은 스크립트 안에서만** 일어난다.
아직 실행되지 않은 다른 `<script>` 의 함수는 그 시점에 **존재하지 않는다.**

```
config.js 로드 중에 prompts.js 의 함수를 부르면 → ReferenceError
```

분할이 안전한 진짜 이유는 하나다:
**모든 파일 로드가 끝난 뒤 `DOMContentLoaded` 에서 함수를 호출하기 때문.**
로드 도중에는 선언만 등록되고 아무것도 실행되지 않는다.

### 1.3 지켜야 할 3원칙

1. **기능 파일에는 함수 선언만 둔다.** 초기화 호출·이벤트 등록은 전부 진입점 파일로.
   파일 최상위에서 뭔가를 *실행*하는 순간 로드 순서에 의존하게 되고 전제가 무너진다.
2. **공유 상태 선언은 한 파일에 모은다** (`config.js`).
   최상위 `let`/`const` 는 스크립트끼리 공유되지만 TDZ가 있어, 선언한 스크립트가
   실행되기 전에 접근하면 `ReferenceError`.
3. **`<script>` 순서를 유지하고 `async` 를 붙이지 않는다.** `async` 는 로드 완료 순서대로
   실행해 순서를 깨뜨린다.

이 3원칙을 지키면 강제되는 순서는 둘뿐이다 — 상태 선언 파일이 맨 먼저, 진입점이 맨 마지막.

### 1.4 섹션 주석 이동 판단 기준

`// ==== Phase N: 무엇 ====` 같은 구분 주석은 기계적으로 따라 옮기면 안 된다.

- **덮는 함수가 전부 이번에 이동** → 주석도 함께 이동
- **하나라도 남는 함수를 덮음** → 원래 자리에 잔류

앞 단계에서 일부 함수가 이미 빠져나가 **섹션이 비어가는 경우**가 생긴다.
예: `Phase 10: 복사 기능` 은 원래 3개를 덮었지만 2개가 먼저 다른 파일로 가서,
마지막 1개가 이동할 때 주석도 함께 갈 수 있게 됐다. 매 단계 다시 판단해야 한다.

함수 바로 위의 설명 주석(`// 5.7: 날짜 포맷팅 함수`)은 항상 함께 옮긴다.

### 1.5 잘라낸 자리의 공백줄

블록을 들어내면 앞뒤 공백줄이 겹치거나 사라진다.
**삭제 범위에 후행 공백줄 1개를 포함**시키면 간격이 원래대로 유지된다.

부작용도 있다. `validateCategory` 를 후행 공백줄까지 잘라내자, 그 자리를 사이에 두고
떨어져 있던 앞뒤 블록이 **하나의 연속 블록으로 붙었다.** 다음 단계에서 "두 덩어리"로
알고 있던 것이 실제로는 한 덩어리였다. **계획서의 줄 번호와 구조는 매 단계 재확인할 것.**

## 2. 무손실 증명 — 리팩터링을 "검증"하는 법

### 2.1 ★ 함수 개수만 세면 누락과 중복이 상쇄된다

하나를 빠뜨리고 다른 하나를 두 번 붙여넣으면 **합계는 그대로**다. 실제로 재현했다:

```
개수 검증:        87 = 87        ← 통과해버림
이름별 본문 비교:
  < formatDate  05cfbc690ef7  7      ← 누락 검출
  > showToast   f16765eda17c  10     ← 중복 검출
```

### 2.2 이름 → 본문 해시 대조를 기본 검증으로

[`tools/fnmap.py`](../tools/fnmap.py) 가 `함수이름 <TAB> 본문md5 <TAB> 줄수` 를 정렬 출력한다.

```bash
snap() { { git show "$1:index.html"; echo
           for f in $(git ls-tree --name-only -r "$1" js/); do git show "$1:$f"; echo; done
         } | python tools/fnmap.py; }
now()  { { cat index.html; echo; for f in js/*.js; do cat "$f"; echo; done; } | python tools/fnmap.py; }

diff <(snap HEAD) <(now)     # 순수 이동이면 차이 0
```

**차이 0 = 이름·본문·줄수가 전부 동일** = 이동 외에 아무것도 안 바뀌었다는 뜻.
개수는 보조 지표로만 본다.

> ⚠ 양쪽을 **같은 정렬 규칙**으로 뽑을 것. 파이썬 `sorted()` 출력에 GNU `sort` 를 다시 걸면
> 로케일 차이로 전체가 어긋난 것처럼 보인다. 실제로 한 번 당했다.

### 2.3 왕복 검증 (CSS 분리 등 비-함수 이동)

분리한 조각을 **다시 합쳐서 원본과 md5 대조**한다.
CSS 1,210줄을 뽑아낸 뒤 `<link>` 자리에 도로 끼워 넣어 원본과 해시가 일치함을 확인했다.
순서·주석·공백·들여쓰기·마지막 줄 개행까지 보존됐다는 증명이 된다.

### 2.4 앵커 assert — 자르기 전에 멈추는 장치

줄 번호로 자르는 스크립트는 **자르기 전에 해당 줄의 내용을 예상값과 대조**한다.

```python
checks = {512: "        // 3.3: LocalStorage 키 이름 정의", ...}
for n, expect in checks.items():
    assert lines[n-1] == expect, "line %d 불일치" % n
```

줄이 밀렸으면 자르기 전에 죽는다. 매 단계 16~42개씩 걸어 썼고, 실제로 계획서의 줄 번호가
틀린 곳을 여러 번 잡아냈다.

### 2.5 공백줄 제외 줄-멀티셋 대조

`grep -v '^[[:space:]]*$' | sort` 로 양쪽을 정렬해 `diff` 하면, 이동 전후에 **의도한 차이만**
남는지 볼 수 있다. 파일 끝에 개행이 없으면 `cat` 이 줄을 이어붙이니 `echo` 를 사이에 끼울 것.


### 2.6 ★ 이름이 같은 메서드가 있으면 죽은 코드 판정이 오판한다

호출부 0건인 함수를 스크립트로 찾을 때, **어댑터 메서드와 이름이 같으면 살아있는 것으로
잘못 잡힌다.**

```
function saveCategories()          ← 최상위. 호출부 0건 (죽은 코드)
PromptStorage.saveCategories(...)  ← 어댑터. 살아있음
```

단순히 `grep -c "saveCategories"` 하면 후자가 잡혀 "아직 쓰인다"고 판정한다.
**접두사를 빼고 베어 호출만 세야 한다.**

```bash
grep -rn "\bsaveCategories(" js/ | grep -v "PromptStorage\.\|this\.adapter\.\|async saveCategories("
```

실제로 자동 스캔은 죽은 함수 4개 중 2개를 놓쳤다. 삭제 전에는 **자동 판정을 그대로 믿지 말고
이름 충돌 후보를 따로 확인한다.** 주석 줄도 제외해야 한다 — 설명 주석에 함수명이 있으면
그것도 "호출부"로 잡힌다.

## 3. `DOMContentLoaded` 리스너를 합치면 예외 격리가 사라진다

원본은 `addEventListener('DOMContentLoaded', ...)` 를 **2회** 호출하고 있었다.
"파일 하나로 합치는 김에" 리스너도 하나로 병합했다가 회귀를 만들었다.

**DOM 명세상 리스너는 서로 격리된다.** 하나가 예외를 던져도 나머지는 실행된다.
합치면 그 격리가 사라져, 초기화 도중 예외 하나에 뒤쪽 등록이 전부 유실된다.

헤드리스 Chrome A/B 대조로 재현 (`initializeData` 에 예외 주입):

```
A · 리스너 2개   close=true  copy=true  edit=true  dup=true  del=true
B · 리스너 1개   close=false copy=false edit=false dup=false del=false
```

→ **파일은 합쳐도 리스너는 합치지 않는다.** 초기화 실패와 무관하게 살아야 하는
이벤트 등록은 별도 리스너로 둔다.

부수 효과: 이후 참고자료 기능을 제거할 때 `setupReferences()` 호출이 리스너1의 마지막
문장이라, 호출을 지우지 않았다면 `ReferenceError` 로 리스너1이 통째로 죽었을 것이다.
**기능을 지울 때는 함수뿐 아니라 호출부를 반드시 함께 지운다.**


### 3.1 async 리스너는 첫 `await` 에서 양보한다

읽기가 비동기가 되면서 리스너1만 `async` 가 됐다. 그러면 **리스너1이 첫 `await` 에서
양보하는 사이 리스너2가 먼저 실행된다.** 등록 순서와 완료 순서가 달라진다.

여기서는 문제가 없었고 오히려 이득이었다 — 리스너2는 **이미 존재하는 정적 DOM 에
이벤트만 등록**하므로 순서를 타지 않고, 리스너1이 중간에 죽어도 살아남는다.

반대로 리스너2가 리스너1이 만든 DOM 을 참조했다면 그 순간 깨졌을 것이다.
**리스너를 async 로 바꿀 때는 뒤 리스너가 앞 리스너의 결과에 의존하는지 먼저 확인한다.**

## 4. 저장 계층 어댑터

### 4.1 ★ `Storage` 는 브라우저 내장 이름이다

`const Storage = {...}` 는 **선언은 된다.** 내장 `Storage` 가 configurable 프로퍼티라
전역 렉시컬 선언이 섀도잉할 수 있기 때문. 하지만 대가가 있다:

```
bare Storage = ours                                    ← 우리 객체
window.Storage = function                              ← 내장은 살아있음
localStorage instanceof window.Storage = true          ← 우회하면 정상
localStorage instanceof Storage → TypeError: Right-hand side of 'instanceof' is not callable
```

→ `PromptStorage` 처럼 접두사를 붙인다. 전역 이름을 정하기 전에 **내장과 충돌하는지
브라우저에서 직접 확인**할 것.

### 4.2 읽기 반환값은 3상태로 나눈다

| 상황 | 반환 | 이유 |
|---|---|---|
| 키 없음 (한 번도 저장 안 됨) | `null` | "저장된 빈 배열"과 구분해야 한다 |
| 파싱 실패 | `throw` | 빈 배열로 덮으면 조용한 데이터 소실 |
| 정상 | 파싱된 값 | |

`null` 과 `[]` 를 뭉개면 안 되는 실제 사례: 기존 코드가
`if (storedCategories) categories = JSON.parse(...) else 기본값` 인데,
`"[]"` 는 truthy라 **빈 배열과 미저장이 다르게 동작**했다. 어댑터가 둘 다 `[]` 로 주면
동작이 바뀐다.

### 4.3 읽기에 실패하면 쓰기를 막는다

깨진 데이터를 읽지 못한 상태에서 자동 저장이 돌면 **원본을 덮어써 복구 불가**가 된다.

- 파싱 실패 시 `isReadFailed` 플래그 + 원본 문자열을 `rawBackup` 에 보관
- 이후 모든 쓰기는 저장하지 않고 경고만 남긴다
- **단, 전체 삭제(`removeAll`)는 가드를 우회한다** — 손상 상태에서 벗어나는 유일한 경로다.
  여기까지 막으면 복구 수단이 없어진다.

### 4.4 동기 → 비동기 전환 비용을 먼저 측정한다

전량 조사에서 나온 수치가 설계를 정했다.

- `localStorage` 직접 호출 **11건 / 3파일** — 생각보다 적었다
- 쓰기 함수 호출부 **21곳이 전부 반환값을 안 쓰는 단독 문장** → Promise로 바꿔도
  호출부는 `await` 만 붙이면 됨
- 모든 쓰기가 컬렉션을 **통째로** 저장 → 단건 API(`savePrompt(p)`)는 지금 구조에 안 맞음.
  전량 방식(`savePrompts(list)`)으로 확정

진짜 비용은 **읽기 쪽 한 곳**에 몰려 있었다. 초기화가 값을 받아 전역에 대입하고
그 뒤 렌더링이 이어지는 구간 — 여기만 `async`/`await` 로 바꾸면 된다.

### 4.5 단계를 쪼갠다

```
인터페이스 정의  →  호출부 교체  →  기존 함수 제거
```

정의 단계에서는 **기존 함수를 한 글자도 건드리지 않는다.** 호출부가 없으니 앱 동작이
지금과 완전히 동일해야 하고, 그게 곧 "아무것도 안 깨졌다"는 증명이 된다.
새 코드는 브라우저에서 별도로 단위 검증한다 (30개 케이스: 왕복 / 3상태 / 실패 경로 /
쓰기 차단 / 복구).


### 4.6 ★ 파싱은 성공하는데 값이 틀린 경우

`JSON.parse` 는 생각보다 관대하다. **예외를 던지지 않는다:**

| 저장된 값 | `JSON.parse` 결과 | 문제 |
|---|---|---|
| `"null"` | `null` | **"키 없음"과 구분되지 않는다** |
| `"123"` `"\"abc\""` `"true"` | 숫자·문자열·불린 | 배열을 기대하는 코드가 깨진다 |
| `"{}"` | 객체 | 위와 동일 |

`"null"` 이 가장 위험하다. 어댑터가 `null` 을 돌려주면 호출부는 "저장된 적 없음"으로 읽고
**기본값을 만들어 저장한다. 그 순간 원본이 사라진다.**

→ 배열 getter 는 `Array.isArray()` 까지 검증하고, 아니면 손상으로 취급해 `throw` 한다.

**역설:** 검증이 없던 기존 코드가 오히려 안전했다. `JSON.parse` 가 던지든 뒤에서 터지든
초기화가 중단돼 원본이 보존됐기 때문이다. **어댑터로 감싸면서 그 우연한 보호를 걷어내지 않도록
의도적으로 다시 세워야 한다.** 추상화가 안전장치를 먹어치우는 전형적인 경우다.

같은 부류의 구멍이 쓰기 쪽에도 있다 — **`JSON.stringify(undefined)` 는 예외 없이
`undefined` 를 반환한다.** 그대로 저장하면 `"undefined"` 문자열이 남아 다음 읽기가 깨진다.
`Array.from(null)`, `String(Symbol())` 처럼 **변환 단계 전체를 try 안에 넣어야** 한다.

### 4.7 읽는 도중에 쓰는 초기화는 순서가 위험하다

초기화 코드는 "없으면 기본값을 쓴다"를 하느라 **읽기와 쓰기가 뒤섞이기 쉽다.**

```
✗ 프롬프트 읽기 → 없으면 저장 → 즐겨찾기 읽기 → 카테고리 읽기
```

이 저장이 프롬프트와 즐겨찾기를 **함께** 쓴다면, 즐겨찾기를 읽기도 전에
빈 값으로 덮어쓴다. 즐겨찾기가 손상돼 있어도 실패 가드가 설 기회조차 없다.

```
✓ 읽기를 전부 끝낸다 → 전역 상태에 대입한다 → 그다음 첫 쓰기
```

**첫 쓰기 전에 관련 읽기를 전부 끝낸다.** 이 한 줄이 규칙의 전부다.

### 4.8 ★ 스냅샷 롤백 — 얕은 복사는 요소를 공유한다

저장이 실패할 수 있게 되는 순간, "메모리 변경 → 저장 → UI 갱신" 순서가 위험해진다.
호출부마다 역연산을 짜면 그 코드가 새 버그가 되므로 **스냅샷 일괄 복원**으로 통일한다.

```js
const snapshot = { prompts: [...allPrompts], favorites: new Set(favoriteIds) };
// 메모리 변경
if (await PromptStorage.savePrompts(allPrompts) !== true) {
    allPrompts = snapshot.prompts;
    favoriteIds = snapshot.favorites;
    applyFilters();
    showToast('저장 실패 — 변경을 되돌렸습니다 ❌');
    return;                      // UI 갱신·성공 토스트로 넘어가지 않는다
}
```

**함정: `[...allPrompts]` 는 요소 객체를 공유한다.**
배열에서 추가·삭제한 것은 되돌리지만, **객체 필드를 제자리에서 바꾼 것은 못 되돌린다.**

| 변경 방식 | 얕은 복사로 롤백 | 대응 |
|---|---|---|
| `push` / `splice` / `unshift` | 가능 | `[...arr]` 로 충분 |
| `obj.field = x` (제자리) | **불가** | 대상 객체 사본 `{...obj}` 를 따로 |
| 여러 요소를 순회하며 제자리 변경 | **불가** | 바뀐 객체만 배열에 모아 개별 복원 |

전량 깊은 복사(`JSON.parse(JSON.stringify(...))`)로 해결할 수도 있지만,
썸네일 base64 때문에 크기가 튄다. **바뀐 것만 기록하는 편이 싸고 정확하다.**

### 4.9 ★ 반환값을 아무도 안 쓰는 호출부는 "쉽다"는 신호가 아니다

동기→비동기 전환 비용을 조사할 때 "쓰기 호출부 21곳이 전부 반환값을 안 쓰는 단독 문장"이
좋은 소식처럼 보였다. `await` 만 붙이면 되니까.

**정반대다.** 반환값을 안 본다는 것은 **저장이 실패해도 아무도 모른다**는 뜻이다.
메모리는 바뀌었고, 화면은 갱신됐고, 성공 토스트까지 떴는데 저장만 안 된 상태.
새로고침하면 조용히 사라진다.

전환이 쉬운 것과 **전환하면서 고쳐야 할 것**은 다른 문제다.
반환값 미사용 호출부를 발견하면 그 개수만큼 롤백을 설계해야 한다.

덤으로 순서도 확인할 것 — 성공 토스트가 저장보다 **먼저** 있는 곳이 있었다.

### 4.10 ★ async 로 바꾸면 Promise 를 받는 곳이 없는 경로가 드러난다

`async` 함수의 예외는 **반환 Promise 로 전달된다.** 그 Promise 를 받는 곳이 없으면
예외는 `unhandledrejection` 으로만 남고 사용자에게는 아무 표시가 없다.

받는 곳이 없는 경로:

| 경로 | 이유 |
|---|---|
| HTML 인라인 `onclick="fn()"` | 반환값을 버린다 |
| `FileReader.onload` | 브라우저가 콜백의 Promise 를 처리하지 않는다 |
| `addEventListener` 핸들러 | 동일 (다만 대개 최상위라 영향이 적다) |

→ **해당 함수 본문 전체를 `try/catch` 로 감싸 자체 처리한다.**
`catch` 에서 `console.error` + 사용자에게 보이는 토스트.

```js
async function toggleFavorite(id) {
    try {
        // ...
    } catch (error) {
        console.error('[즐겨찾기] 처리 실패:', error);
        showToast('즐겨찾기 처리 중 오류가 발생했습니다 ❌');
    }
}
```

검증할 때는 **어댑터가 `throw` 하도록 주입하고 `unhandledrejection` 이 0건인지** 본다.
`false` 반환만 테스트하면 이 경로는 잡히지 않는다.

### 4.11 ★ 실패 가드의 범위는 데이터 단위로 잡는다

읽기에 실패했을 때 쓰기를 막는 것까지는 옳았는데, 플래그를 **전역 하나**로 뒀다가
범위가 과해졌다.

```
promptDictionary_searchHistory 하나가 깨짐
  → 프롬프트·카테고리·즐겨찾기·테마 저장이 전부 차단
  → 화면은 멀쩡히 뜨고, 사용자는 모든 동작에서 "저장 실패"만 본다
  → 원인 안내 없음. 복구는 콘솔에서 removeAll() 뿐
```

최근 검색어 5개가 깨졌다고 프롬프트를 못 쓰게 만들 이유가 없다.

```js
failedKeys: new Set(),
_blockedByReadFailure(key, label) {
    if (!this.failedKeys.has(key)) return false;
    ...
}
```

**두 가지가 같이 필요하다:**
1. **범위** — 손상된 키만 잠근다. 멀쩡한 데이터는 계속 저장된다
2. **고지** — 실패 메시지에 **원인 키**를 실는다. 원인을 모르면 사용자는
   같은 동작을 반복하거나 앱이 고장 났다고 판단한다

> 실측: 전역 플래그일 때 프롬프트 추가·즐겨찾기·카테고리·테마가 전부 `false`.
> 키 단위로 바꾼 뒤 검색 기록만 `false`, 나머지 4종은 `true`.

### 4.12 ★ 파사드는 어댑터의 rejection 을 공개 규약으로 정규화해야 한다

가장 놓치기 쉬운 구멍이었다. 호출부는 이렇게 생겼다:

```js
if (await PromptStorage.savePrompts(allPrompts) !== true) {
    allPrompts = snapshot.prompts;   // 롤백
    ...
    return;
}
```

**어댑터가 `reject` 하면 이 `if` 자체에 도달하지 못한다.** `await` 가 예외를 던져
함수를 빠져나가므로 **롤백 분기를 통째로 건너뛴다.** 결과:

- 저장은 실패했는데 **메모리에는 변경이 남는다**
- 화면도 그 상태로 남는다
- 나중에 **다른 저장이 성공하면 그 변경까지 함께 저장된다** (뒤늦은 오염)

`false` 반환만 테스트하면 절대 안 잡힌다. **어댑터가 던지도록 주입해서** 테스트해야 한다.

```js
async _safeWrite(label, run) {
    try {
        return await run();
    } catch (error) {
        console.error('[PromptStorage] ' + label + ' 저장 중 예외 — false 로 처리합니다:', error);
        return false;
    }
}
```

**전역 `unhandledrejection` 핸들러가 있어도 해결되지 않는다.** 그것은 예외를 *알릴* 뿐
**롤백을 실행시키지 못한다.** 안전망이지 해결책이 아니다 — 이 둘을 헷갈리면
"핸들러를 달았으니 됐다"고 넘어가게 된다.

정규화는 **호출부를 한 곳도 고치지 않고** 19곳의 롤백을 전부 되살린다.
경계(파사드)에서 규약을 강제하는 것이 개별 호출부를 손보는 것보다 싸고 확실하다.

### 4.13 읽기와 쓰기의 실패 처리는 대칭일 필요가 없다

쓰기를 `false` 로 정규화했다고 읽기까지 정규화하면 안 된다.

| | 실패 표현 | 이유 |
|---|---|---|
| 쓰기 | `false` | 호출부가 롤백을 실행해야 한다. 예외는 그 분기를 건너뛴다 |
| 읽기 | `throw` | **"손상"과 "키 없음"이 다시 섞이면** §4.6의 구멍이 되살아난다 |

읽기를 `null` 로 뭉개는 순간 호출부는 "저장된 적 없음"으로 읽고 기본값을 써서
원본을 덮는다. **비대칭이 맞다.** 코드에 주석으로 이유를 남겨야 나중에 누군가
"일관성"을 이유로 통일하려 든다.

### 4.14 진단용 값은 "가드의 입력이 아니라 결과"임을 명시한다

`isReadFailed` 를 지우지 않고 getter 로 남겼다. 콘솔에서 한눈에 보는 값이라 쓸모가 있다.

```js
// 하위 호환·진단용 요약 값. 가드의 입력이 아니라 결과다.
// 쓰기 차단 여부는 항상 failedKeys.has(key) 로 판단한다.
get isReadFailed() { return this.failedKeys.size > 0; }
```

이 주석이 없으면 다음 사람이 `if (PromptStorage.isReadFailed) return;` 같은 코드를
쓰고, 키 단위로 바꾼 의미가 사라진다. **요약 값을 남길 때는 그것으로 분기하지 말라고
같이 적는다.** 읽기 전용(getter)으로 만들어 대입을 막는 것도 같은 목적이다.

### 4.15 읽기 실패 가드는 "읽힌 키"에만 걸린다

`failedKeys` 는 실제로 읽어본 키만 기록한다. 초기화가 **첫 읽기에서 `throw` 하면
뒤 키들은 검사조차 되지 않으므로**, 그 키가 손상돼 있어도 잠기지 않는다.

설계상 무해하다 — 초기화가 중단되면 렌더링도 setup 도 실행되지 않아
**사용자가 쓰기를 유발할 경로 자체가 없다.** 하지만 이 성질을 모르면
"손상됐는데 왜 안 잠기지?" 하고 헤매게 된다.

> 검증을 짜다가 이걸 몰라 기댓값을 틀리게 잡았다. 세 키를 동시에 손상시키면
> `failedKeys` 가 3개일 거라 예상했지만 실제로는 첫 실패 키 1개뿐이었다.

### 4.16 ★ 브라우저 API 의 보안 컨텍스트 제약

`crypto.randomUUID()` 는 **보안 컨텍스트 전용**이다 — `https`, `localhost`, 그리고 `file://`.

개발 중에는 `file://` 로 열기 때문에 멀쩡히 동작한다. 그런데 **http 로 서비스하는 순간
`undefined` 가 되어 조용히 깨진다.** 이 프로젝트는 P4에서 `http:8807` 로 올릴 예정이라
그대로 뒀으면 배포 시점에 ID 생성이 통째로 멈췄을 것이다.

```js
if (typeof crypto !== 'undefined' && typeof crypto.randomUUID === 'function') {
    return crypto.randomUUID();
}
// getRandomValues 는 비보안 컨텍스트에서도 쓸 수 있다
if (typeof crypto !== 'undefined' && typeof crypto.getRandomValues === 'function') {
    const bytes = crypto.getRandomValues(new Uint8Array(16));
    bytes[6] = (bytes[6] & 0x0f) | 0x40;   // version 4
    bytes[8] = (bytes[8] & 0x3f) | 0x80;   // variant 10
    // ... hex 로 조립
}
throw new Error('이 브라우저에서는 안전한 ID를 생성할 수 없습니다.');
```

**`Math.random` 으로 떨어뜨리지 않는다.** 충돌 회피가 목적인데 약한 난수로 대체하면
같은 문제가 조용히 남는다. 둘 다 없으면 `throw` 한다 — 조용한 실패보다 낫다.

→ **배포 환경의 프로토콜을 미리 확인한다.** 보안 컨텍스트를 요구하는 API 는
`crypto.subtle`, `navigator.clipboard`, `getUserMedia`, Service Worker 등 여럿이다.
`file://` 에서 된다고 http 에서도 된다는 보장이 없다.

> 참고: `copyToClipboard` 가 `navigator.clipboard` 실패 시 `fallbackCopy` 로 떨어지는
> 구조인 것도 같은 이유다. 그쪽은 이미 폴백이 있었다.

### 4.17 ★ 식별자 타입을 바꾸면 파싱·비교 코드가 함께 깨진다

`Date.now()` → UUID 전환은 "생성 지점 5곳만 바꾸면 되는" 작업처럼 보였다.
실제로는 **읽는 쪽이 더 많았다.**

```js
const id = parseInt(this.dataset.id);   // UUID → NaN
```

`parseInt` 4곳이 전부 `NaN` 이 되어 카드 클릭·수정 대상 조회·전체 선택·
체크박스 동기화가 한꺼번에 실패한다. 생성 지점만 고치고 넘어갔다면 앱이 통째로 깨졌다.

인라인 `onclick` 도 함께 깨진다:

```html
onclick="toggleFavorite(${prompt.id})"     <!-- toggleFavorite(a3f2-9b1c-…) → 구문 오류 -->
onclick="toggleFavorite('${prompt.id}')"   <!-- 따옴표 필요 -->
```

숫자일 때는 따옴표가 없어도 됐기 때문에 드러나지 않던 문제다.

→ **타입을 바꿀 때는 생성 지점이 아니라 소비 지점을 전수 조사한다.**

| 찾을 것 | 이유 |
|---|---|
| `parseInt` / `Number(` / `+id` | 숫자 변환이 깨진다 |
| `===` / `!==` 비교 | 타입이 섞이면 조용히 false |
| `Set.has` / `Map.get` / `includes` | 위와 같음. 특히 `favoriteIds` |
| 템플릿 삽입 `${id}` | 따옴표 필요 여부가 바뀐다 |
| `dataset.*` | DOM 속성은 항상 문자열이다 |

`dataset` 이 항상 문자열이라는 점이 핵심이다. 숫자 id 시절에는 `parseInt` 로
되돌려야 했고, 문자열 id 로 바꾸면 그 `parseInt` 가 정확히 반대로 작동한다.

## 5. 환경 함정

### 5.1 `.gitattributes` 로 줄바꿈을 고정한다

`core.autocrlf=true` 인 Windows에서 `git add` 시 경고가 뜬다.
저장소에는 LF로 들어가지만, **다시 clone하면 워킹 파일이 CRLF** 가 되어 원본 대조가 깨진다.

```
* text=auto eol=lf
*.png binary
```

적용 후 `git add --renormalize .` 로 기존 파일에 변화가 없는지 확인한다.
`git ls-files --eol` 로 `i/lf w/lf` 를 눈으로 볼 것.

### 5.2 PowerShell here-string 을 Bash에 쓰지 말 것

`@'...'@` 는 PowerShell 문법이다. Bash 툴에 넣으면 `@` 가 문자 그대로 들어가
커밋 메시지 첫 줄이 `@` 가 된다. 실제로 한 번 당했고 push 전 `--amend` 로 고쳤다.

Bash에서 여러 줄 메시지는 **heredoc + `git commit -F`**:

```bash
cat > msg.txt <<'EOF'
제목

본문
EOF
git commit -F msg.txt
```

heredoc 안에 따옴표·백틱이 많은 코드를 넣으면 파싱이 깨지기도 한다.
그럴 땐 파일을 직접 쓰는 편이 안전하다.

### 5.3 `\n` `\t` 가 문서에 실제 줄바꿈으로 박히는 사고

스크립트로 문서를 생성할 때, 문서 안에 들어갈 **코드 예제의 이스케이프**가
한 번 더 해석돼 실제 줄바꿈/탭이 되어 코드가 깨진 채 저장됐다.

→ **문서에 넣은 코드는 문서에서 다시 뽑아 실행해 본다.** `sed` 로 코드블록을 추출해
돌려보면 즉시 드러난다.

### 5.4 ★ "초기화 완료" 로그는 검증 근거가 아니다

인라인 `<script>` 최상위의 `console.log('... 완료 ✅')` 는 **파싱 시점에 즉시** 출력된다.
`DOMContentLoaded` 초기화보다 **먼저** 찍힌다.

→ 콘솔에 "완료"가 보여도 초기화가 성공했다는 뜻이 아니다. 초기화가 첫 줄에서 터져도
그 로그는 그대로 찍힌다. **동작 확인은 화면과 실제 조작으로 한다.**

### 5.5 헤드리스 브라우저로 실제 검증하기

`node --check` 는 구문만 본다. 동작은 진짜 브라우저로 확인한다.

```bash
chrome.exe --headless=new --disable-gpu --no-sandbox \
  --virtual-time-budget=8000 --user-data-dir=<임시> \
  --dump-dom "file:///.../index.html" | grep -o '<div id="RESULT">[^<]*</div>'
```

프로브 스크립트를 임시 사본에 주입해 결과를 DOM에 써넣고 `--dump-dom` 으로 회수한다.
`window.addEventListener('error', ...)` 로 미처리 예외를 세면 "예외 0건"을 증명할 수 있다.
`alert` 은 가로채 기록만 하도록 덮어써야 멈추지 않는다.

### 5.6 `CLAUDE.md` 는 저장소 루트에 둔다

세션 시작 시 자동으로 읽히는 위치다. 하위 폴더에 두면 로드되지 않는다.

### 5.7 붙여넣기 허용 설정

긴 텍스트를 터미널에 붙여넣을 때 클라이언트가 확인을 요구할 수 있다.
계획서·프롬프트처럼 긴 입력을 자주 넣는 작업에서는 미리 허용해두면 흐름이 끊기지 않는다.


### 5.8 ★ 헤드리스 자동검증이 거짓말하는 두 가지

**`--virtual-time-budget` 은 타이머만 앞당긴다.**
`setTimeout` 은 즉시 소진되지만 `FileReader` 같은 **실제 I/O 는 건너뛸 수 없다.**
"파일을 읽히고 250ms 기다린다"는 코드는 읽기가 끝나기 전에 통과해버린다.

```js
// ✗ virtual time 에서 즉시 지나간다
importData(fake); await sleep(250);

// ✓ 실제 신호를 기다린다
var before = toasts.length;
importData(fake);
await poll(() => toasts.length > before);
```

실제로 이 함정 때문에 멀쩡한 코드가 FAIL 로 나왔고, 어댑터를 단독 진단해서야
테스트 쪽 문제임이 드러났다. **검증이 실패하면 코드를 의심하기 전에 검증을 의심한다.**

**`<a download>` 클릭은 `--dump-dom` 을 끝나지 않게 만든다.**
`exportData()` 처럼 앵커를 만들어 `click()` 하는 코드가 있으면 헤드리스가 멈춘다.
앵커 클릭을 가로채면 되고, 덤으로 파일명까지 검증 항목이 된다.

```js
HTMLAnchorElement.prototype.click = function () { window.__downloads.push(this.download); };
```

`alert` / `confirm` / `prompt` 도 미리 덮어써야 멈추지 않는다.

> ⚠ 백그라운드로 돌린 검증이 있는 상태에서 `taskkill /F /IM chrome.exe` 를 하면
> 그 검증이 통째로 빈 결과가 된다. 실제로 한 번 날렸다.

### 5.9 ★ 가상 시간에서 CSS transition 이 얼어 `getComputedStyle` 이 시작값을 준다

`transition: all 0.2s` 가 걸린 요소의 계산 스타일을 헤드리스에서 읽으면
**전이 후 값이 아니라 시작값**이 나온다. 클래스는 제대로 붙었는데
"스타일이 안 먹는다"고 오판하게 된다.

```js
btn.classList.add('active');          // class = "toolbar-btn active" ✓
getComputedStyle(btn).backgroundColor // rgb(108,117,125)  ← 꺼짐 색 그대로
```

T-208에서 `.toolbar-btn.active` 가 적용되지 않는 줄 알고 CSS 명시도·충돌 규칙을
한참 뒤졌다. **CSS 는 처음부터 맞았다.**

```js
btn.style.transition = 'none';
void btn.offsetHeight;                // 강제 reflow
getComputedStyle(btn).backgroundColor // rgb(66,99,235)  ← --accent-primary
```

→ **검증 시 트랜지션을 끈다.** 전체를 한 번에 끄는 편이 안전하다.

```js
var s = document.createElement('style');
s.textContent = '* { transition: none !important; animation: none !important; }';
document.head.appendChild(s);
```

#### 시계도 얼어 있다 — 성능 측정이 불가능하다

같은 이유로 **`Date.now()` 와 `performance.now()` 가 둘 다 멈춘다.**
동기 코드 안에서는 값이 변하지 않아, 50회를 반복해도 경과 시간이 `0ms` 로 나온다.

```
가상 시간   : 150행 renderBulkPreview x50 → 0ms   (측정 불가)
가상 시간 끔: 150행 renderBulkPreview     → 191ms
```

성능을 재려면 `--virtual-time-budget` 을 빼고, 모든 작업을 `load` 핸들러 안에서
**동기로** 끝내야 한다 (그래야 `--dump-dom` 이 결과를 잡는다).

#### 정리 — 가상 시간은 "시간에 의존하는 모든 것"을 앞당기지 않는다

| 대상 | 가상 시간에서 |
|---|---|
| `setTimeout` / `setInterval` | **즉시 소진** (§5.8) |
| 실제 I/O (`FileReader`, `fetch`) | 건너뛰지 못한다 (§5.8) |
| CSS transition / animation | **얼어서 시작값이 남는다** |
| `Date.now()` / `performance.now()` | **멈춰서 경과가 0** |

앞의 둘은 "너무 빨라서" 틀리고, 뒤의 둘은 "멈춰서" 틀린다.
방향이 반대라 한 가지 대처로 덮이지 않는다 —
**타이밍은 실제 신호를 기다리고, 스타일과 성능은 가상 시간을 끄고 잰다.**

## 6. 검수 배치 — 기계는 매 단계, 사람은 분기점에

**기계 검증은 매 단계 전부 돌린다.** 싸고 빠르다.
`fnmap` 대조 → 개수 → `node --check` → 전 파일 이어붙여 중복 선언 검사 → 헤드리스 실행.

**사람(Codex) 검수는 분기점에 배치한다.** 매 커밋마다 부르면 비용만 든다.
실제로 사람 검수가 잡아낸 것은 기계가 절대 못 잡는 종류였다:

- `DOMContentLoaded` 병합으로 **예외 격리가 사라진 것** (§3) — 구문·해시 전부 통과했다
- 계획서의 **사실 오류** (`renderCategoryDropdown` 에 있지도 않은 호출을 지우라는 지시)
- **개수 검증의 상쇄 맹점** (§2.1)
- "호이스팅이라 안전하다"는 **틀린 근거** (§1.2)

→ 기계는 "바뀌었는가"를 보고, 사람은 "이 설계가 맞는가"를 본다. 역할이 다르다.
그리고 **검수에서 나온 지적은 코드뿐 아니라 계획서에도 반영**해야 같은 실수가 반복되지 않는다.

### 6.1 ★ 테스트가 실제 사용자 경로를 우회하면 통과해도 아무것도 증명하지 못한다

T-101에서 "카테고리 필수 검증 해제"를 하고 **45/45 통과**를 받았다.
그런데 실제 사용자는 여전히 카테고리를 골라야 했다.

```html
<select id="prompt-category" required>   <!-- 이게 남아 있었다 -->
```

JS 쪽 `if (!category) { alert(...); return; }` 만 지웠고, **HTML 의 `required` 는 그대로**였다.
브라우저가 제출 자체를 막으므로 JS 는 실행되지도 않는다.

**테스트가 이걸 놓친 이유:**

```js
form.dispatchEvent(new Event('submit'))   // ✗ 네이티브 폼 검증을 건너뛴다
form.requestSubmit()                      // ✓ 검증을 거쳐 제출한다
```

`dispatchEvent` 는 그냥 이벤트를 쏘는 것이라 제약 검증(constraint validation)을 타지 않는다.
그래서 테스트는 **"JS 코드가 바뀌었다"는 것만 증명**하고 통과했다.

#### 일반화

**테스트가 실제 진입 경로와 다른 경로를 타면, 그 테스트는
"코드가 바뀌었다"는 증명은 되지만 "기능이 동작한다"는 증명은 안 된다.**

같은 이유로 T-009c-2에서는 인라인 `onclick` 함수를 **직접 호출하지 않고
실제 버튼을 클릭**해서 검증했다. 직접 호출하면 `onclick` 속성 문자열이
잘못됐어도(따옴표 누락 등) 테스트는 통과한다.

| 검증 대상 | ✗ 우회하는 방법 | ✓ 실제 경로 |
|---|---|---|
| 폼 제출 | `dispatchEvent(new Event('submit'))` | `form.requestSubmit()` / 제출 버튼 클릭 |
| 인라인 `onclick` | 함수를 직접 호출 | `querySelector('[onclick^="..."]').click()` |
| 카드 클릭 | `openDetailModal(id)` 호출 | `card.click()` |
| 파일 업로드 | 파서 함수에 문자열 전달 | `File` 객체를 만들어 `FileReader` 경유 |

경로를 우회할수록 테스트는 빠르고 안정적이지만, **검증 범위가 그만큼 줄어든다.**
빠른 단위 검증과 실제 경로 검증을 **둘 다** 두는 편이 낫다 —
`suggestTitle` 같은 순수 함수는 직접 호출로 케이스를 많이 돌리고,
"폼에 넣고 저장한다"는 경로는 `requestSubmit` 으로 한 번 태운다.

#### 곁들여: 같은 규칙이 두 겹으로 걸려 있을 수 있다

입력 제약은 **HTML 속성과 JS 검증에 이중으로** 존재하기 쉽다.

```
required / minlength / pattern / type="email"   ← 브라우저가 강제
if (!value) { alert(...); return; }             ← JS 가 강제
```

한쪽만 고치면 **반쪽만 고쳐진다.** 그리고 어느 쪽이 남았는지는
우회 경로로 테스트하는 한 드러나지 않는다.
검증 규칙을 바꿀 때는 **HTML 과 JS 를 같이 grep** 한다.

#### 안 보이는 `required` 는 원인을 알려주지 않는다

T-102에서 폼의 고급 필드를 접었다. 접힌 영역(`display: none`) 안에 `required` 가 있으면
브라우저가 제출을 막으면서도 **어디가 문제인지 보여주지 못한다** —
포커스를 줄 수 없는 요소라 "An invalid form control is not focusable" 로만 끝난다.

→ **접힌 영역에 `required` 가 없다**를 구조 검증 항목으로 고정했다.

```js
ok('접힌 영역에 required 0건', adv().querySelectorAll('[required]').length === 0);
ok('폼 유효성 통과', form.checkValidity());
```

## 7. 자료 이관

### 7.1 이미지 프롬프트 소스 — PPTX (D1 2회차, P4 이후)

테스트 파일: **나노 바나나 템플릿 33장**

구조는 완전히 규칙적이라 추출 자체는 어렵지 않다.

| 항목 | 값 |
|---|---|
| 슬라이드 구성 | 이미지 1 + 텍스트박스 1 |
| 텍스트 길이 | 평균 752자 (306~1,755) |
| 추출 방법 | `python-pptx` |

#### ★ 한 파일 안에서도 형식이 두 가지다

| 슬라이드 | 형식 | 시작 | 구분 정보 |
|---|---|---|---|
| 1~10 | YAML풍 디자인 스펙 | 첫 줄이 전부 `전체 디자인 설정:` | `톤: "..."` 줄 |
| 11~33 | 자유형 지시문 | `**[AI Instruction: ...]**` | 톤 줄이 **없다** |

"한 파일 = 한 형식"을 전제하면 절반이 어긋난다. **파일 단위가 아니라
조각 단위로 형식을 판정**해야 한다.

#### ★ 지금 이관할 수 없는 이유 — 용량

```
이미지 33장 = 19MB → base64 26MB
localStorage 한계 5MB → 8~9장이면 꽉 찬다   (B4)
```

base64는 원본보다 약 1.37배로 불어난다. 지금 구조(`thumbnailImage` 에 data URI)로는
**한 파일도 다 못 넣는다.** 서버에서 파일로 저장하고 경로만 참조하도록 바꾼
뒤에야 가능하다 (T-308).

#### ★ 이미지가 부속물이 아니라 본체다

이 판단이 소스 분류를 갈랐다. "네온 사인 스타일" 33개를 **글로만 읽고
구분하는 것은 사실상 불가능하다.** 텍스트만 먼저 넣으면 나중에 33개를
하나씩 다시 열어 이미지를 붙여야 한다 — 이관을 두 번 하는 셈이다.

→ **소스를 두 갈래로 나눈다.**

| 갈래 | 소스 | 시점 |
|---|---|---|
| 이미지 없는 것 | 메모장 · 카톡 · LLM 대화기록 | **D1 1회차 (지금)** |
| 이미지가 필수인 것 | PPTX 등 | **D1 2회차 (P4 이후)** |

"일단 텍스트만 넣고 이미지는 나중에"가 자연스러워 보이지만, 이미지가
식별자 역할을 하는 자료에서는 그 순서가 작업을 두 배로 만든다.

#### ★ `suggestTitle` 의 약점 발견

**첫 줄이 전부 같은 문서 묶음에서 제목이 전부 같아진다.** 슬라이드 1~10이
모두 `전체 디자인 설정:` 으로 시작하므로 제목 10개가 동일해진다.
[T-103](./worklog/2026-09-08.md)에서 "첫 줄이 역할 지정이어도 그대로 쓴다"고
정한 판단은 유효하지만, **같은 첫 줄이 반복되는 묶음**은 상정하지 않았다.

**실측 결과** (`suggestTitle` 직접 호출):

```
입력 (슬라이드 1~10 형식)   → "전체 디자인 설정:"
입력 (슬라이드 11~33 형식)  → "**[AI Instruction: 네온 사인 스타일로…"
입력 "* 진짜 불릿 항목입니다"  → "진짜 불릿 항목입니다"

첫 줄이 같은 두 문서의 제목이 동일한가 → true
```

- **제목 전부 동일은 사실이다.** 슬라이드 1~10의 제목이 `전체 디자인 설정:` 하나로 수렴한다
- **불릿 제거 규칙과는 충돌하지 않는다.** `^[-*+]\s+` 는 `*` 뒤에 공백을 요구하는데
  `**[` 에는 공백이 없다. 대신 **별표가 제목에 그대로 남는다** —
  충돌이 아니라 다른 문제였다. 마크다운 강조 표기를 벗기는 규칙 자체가 없다

→ **T-104 미리보기에 "제목 중복" 경고 추가를 검토한다.**
지금은 본문 중복만 감지한다(§4 기준). 본문이 다른데 제목만 같은 경우가
정확히 이 사례다.

#### ★ P3 스키마에 반영할 것

**한 프롬프트에 이미지가 여러 장일 수 있는지** 정해야 한다.
`thumbnail_path` 컬럼 하나로는 부족할 수 있다 — 결정 전에 실제 소스에서
"프롬프트 하나에 결과 이미지 여러 장" 패턴이 있는지 확인한다.
