# devlog — 기술 기록

재사용 가치가 있는 원리·함정·패턴을 **주제별로** 축적한다. 날짜순 아님.
그날 무엇을 했는지는 [`worklog/`](./worklog/), 왜 그렇게 정했는지는 [`decisions/`](./decisions/).

## 1. 단일 HTML 분할

### 1.1 일반 `<script>` 는 전역 공간을 공유한다

ES 모듈이 아니면 `import`/`export` 가 없고, 여러 `<script>` 가 **하나의 전역 공간**을 쓴다.
그래서 함수를 어느 파일에 넣든 서로 호출된다.

### 1.2 ★ "호이스팅이라 순서 무관"은 틀린 설명

호이스팅은 **같은 스크립트 안에서만** 일어난다.
아직 실행되지 않은 다른 `<script>` 의 함수는 그 시점에 **존재하지 않는다.**

```
config.js 로드 중에 prompts.js 의 함수를 부르면 → ReferenceError
```

분할이 안전한 진짜 이유는 하나다:
**모든 파일 로드가 끝난 뒤 `DOMContentLoaded` 에서 함수를 호출하기 때문.**
로드 도중에는 선언만 등록되고 아무것도 실행되지 않는다.

### 1.3 지켜야 할 3원칙

1. **기능 파일에는 함수 선언만 둔다.** 초기화 호출·이벤트 등록은 전부 진입점 파일로.
   파일 최상위에서 뭔가를 *실행*하는 순간 로드 순서에 의존하게 되고 전제가 무너진다.
2. **공유 상태 선언은 한 파일에 모은다** (`config.js`).
   최상위 `let`/`const` 는 스크립트끼리 공유되지만 TDZ가 있어, 선언한 스크립트가
   실행되기 전에 접근하면 `ReferenceError`.
3. **`<script>` 순서를 유지하고 `async` 를 붙이지 않는다.** `async` 는 로드 완료 순서대로
   실행해 순서를 깨뜨린다.

이 3원칙을 지키면 강제되는 순서는 둘뿐이다 — 상태 선언 파일이 맨 먼저, 진입점이 맨 마지막.

### 1.4 섹션 주석 이동 판단 기준

`// ==== Phase N: 무엇 ====` 같은 구분 주석은 기계적으로 따라 옮기면 안 된다.

- **덮는 함수가 전부 이번에 이동** → 주석도 함께 이동
- **하나라도 남는 함수를 덮음** → 원래 자리에 잔류

앞 단계에서 일부 함수가 이미 빠져나가 **섹션이 비어가는 경우**가 생긴다.
예: `Phase 10: 복사 기능` 은 원래 3개를 덮었지만 2개가 먼저 다른 파일로 가서,
마지막 1개가 이동할 때 주석도 함께 갈 수 있게 됐다. 매 단계 다시 판단해야 한다.

함수 바로 위의 설명 주석(`// 5.7: 날짜 포맷팅 함수`)은 항상 함께 옮긴다.

### 1.5 잘라낸 자리의 공백줄

블록을 들어내면 앞뒤 공백줄이 겹치거나 사라진다.
**삭제 범위에 후행 공백줄 1개를 포함**시키면 간격이 원래대로 유지된다.

부작용도 있다. `validateCategory` 를 후행 공백줄까지 잘라내자, 그 자리를 사이에 두고
떨어져 있던 앞뒤 블록이 **하나의 연속 블록으로 붙었다.** 다음 단계에서 "두 덩어리"로
알고 있던 것이 실제로는 한 덩어리였다. **계획서의 줄 번호와 구조는 매 단계 재확인할 것.**

## 2. 무손실 증명 — 리팩터링을 "검증"하는 법

### 2.1 ★ 함수 개수만 세면 누락과 중복이 상쇄된다

하나를 빠뜨리고 다른 하나를 두 번 붙여넣으면 **합계는 그대로**다. 실제로 재현했다:

```
개수 검증:        87 = 87        ← 통과해버림
이름별 본문 비교:
  < formatDate  05cfbc690ef7  7      ← 누락 검출
  > showToast   f16765eda17c  10     ← 중복 검출
```

### 2.2 이름 → 본문 해시 대조를 기본 검증으로

[`tools/fnmap.py`](../tools/fnmap.py) 가 `함수이름 <TAB> 본문md5 <TAB> 줄수` 를 정렬 출력한다.

```bash
snap() { { git show "$1:index.html"; echo
           for f in $(git ls-tree --name-only -r "$1" js/); do git show "$1:$f"; echo; done
         } | python tools/fnmap.py; }
now()  { { cat index.html; echo; for f in js/*.js; do cat "$f"; echo; done; } | python tools/fnmap.py; }

diff <(snap HEAD) <(now)     # 순수 이동이면 차이 0
```

**차이 0 = 이름·본문·줄수가 전부 동일** = 이동 외에 아무것도 안 바뀌었다는 뜻.
개수는 보조 지표로만 본다.

> ⚠ 양쪽을 **같은 정렬 규칙**으로 뽑을 것. 파이썬 `sorted()` 출력에 GNU `sort` 를 다시 걸면
> 로케일 차이로 전체가 어긋난 것처럼 보인다. 실제로 한 번 당했다.

### 2.3 왕복 검증 (CSS 분리 등 비-함수 이동)

분리한 조각을 **다시 합쳐서 원본과 md5 대조**한다.
CSS 1,210줄을 뽑아낸 뒤 `<link>` 자리에 도로 끼워 넣어 원본과 해시가 일치함을 확인했다.
순서·주석·공백·들여쓰기·마지막 줄 개행까지 보존됐다는 증명이 된다.

### 2.4 앵커 assert — 자르기 전에 멈추는 장치

줄 번호로 자르는 스크립트는 **자르기 전에 해당 줄의 내용을 예상값과 대조**한다.

```python
checks = {512: "        // 3.3: LocalStorage 키 이름 정의", ...}
for n, expect in checks.items():
    assert lines[n-1] == expect, "line %d 불일치" % n
```

줄이 밀렸으면 자르기 전에 죽는다. 매 단계 16~42개씩 걸어 썼고, 실제로 계획서의 줄 번호가
틀린 곳을 여러 번 잡아냈다.

### 2.5 공백줄 제외 줄-멀티셋 대조

`grep -v '^[[:space:]]*$' | sort` 로 양쪽을 정렬해 `diff` 하면, 이동 전후에 **의도한 차이만**
남는지 볼 수 있다. 파일 끝에 개행이 없으면 `cat` 이 줄을 이어붙이니 `echo` 를 사이에 끼울 것.

## 3. `DOMContentLoaded` 리스너를 합치면 예외 격리가 사라진다

원본은 `addEventListener('DOMContentLoaded', ...)` 를 **2회** 호출하고 있었다.
"파일 하나로 합치는 김에" 리스너도 하나로 병합했다가 회귀를 만들었다.

**DOM 명세상 리스너는 서로 격리된다.** 하나가 예외를 던져도 나머지는 실행된다.
합치면 그 격리가 사라져, 초기화 도중 예외 하나에 뒤쪽 등록이 전부 유실된다.

헤드리스 Chrome A/B 대조로 재현 (`initializeData` 에 예외 주입):

```
A · 리스너 2개   close=true  copy=true  edit=true  dup=true  del=true
B · 리스너 1개   close=false copy=false edit=false dup=false del=false
```

→ **파일은 합쳐도 리스너는 합치지 않는다.** 초기화 실패와 무관하게 살아야 하는
이벤트 등록은 별도 리스너로 둔다.

부수 효과: 이후 참고자료 기능을 제거할 때 `setupReferences()` 호출이 리스너1의 마지막
문장이라, 호출을 지우지 않았다면 `ReferenceError` 로 리스너1이 통째로 죽었을 것이다.
**기능을 지울 때는 함수뿐 아니라 호출부를 반드시 함께 지운다.**

## 4. 저장 계층 어댑터

### 4.1 ★ `Storage` 는 브라우저 내장 이름이다

`const Storage = {...}` 는 **선언은 된다.** 내장 `Storage` 가 configurable 프로퍼티라
전역 렉시컬 선언이 섀도잉할 수 있기 때문. 하지만 대가가 있다:

```
bare Storage = ours                                    ← 우리 객체
window.Storage = function                              ← 내장은 살아있음
localStorage instanceof window.Storage = true          ← 우회하면 정상
localStorage instanceof Storage → TypeError: Right-hand side of 'instanceof' is not callable
```

→ `PromptStorage` 처럼 접두사를 붙인다. 전역 이름을 정하기 전에 **내장과 충돌하는지
브라우저에서 직접 확인**할 것.

### 4.2 읽기 반환값은 3상태로 나눈다

| 상황 | 반환 | 이유 |
|---|---|---|
| 키 없음 (한 번도 저장 안 됨) | `null` | "저장된 빈 배열"과 구분해야 한다 |
| 파싱 실패 | `throw` | 빈 배열로 덮으면 조용한 데이터 소실 |
| 정상 | 파싱된 값 | |

`null` 과 `[]` 를 뭉개면 안 되는 실제 사례: 기존 코드가
`if (storedCategories) categories = JSON.parse(...) else 기본값` 인데,
`"[]"` 는 truthy라 **빈 배열과 미저장이 다르게 동작**했다. 어댑터가 둘 다 `[]` 로 주면
동작이 바뀐다.

### 4.3 읽기에 실패하면 쓰기를 막는다

깨진 데이터를 읽지 못한 상태에서 자동 저장이 돌면 **원본을 덮어써 복구 불가**가 된다.

- 파싱 실패 시 `isReadFailed` 플래그 + 원본 문자열을 `rawBackup` 에 보관
- 이후 모든 쓰기는 저장하지 않고 경고만 남긴다
- **단, 전체 삭제(`removeAll`)는 가드를 우회한다** — 손상 상태에서 벗어나는 유일한 경로다.
  여기까지 막으면 복구 수단이 없어진다.

### 4.4 동기 → 비동기 전환 비용을 먼저 측정한다

전량 조사에서 나온 수치가 설계를 정했다.

- `localStorage` 직접 호출 **11건 / 3파일** — 생각보다 적었다
- 쓰기 함수 호출부 **21곳이 전부 반환값을 안 쓰는 단독 문장** → Promise로 바꿔도
  호출부는 `await` 만 붙이면 됨
- 모든 쓰기가 컬렉션을 **통째로** 저장 → 단건 API(`savePrompt(p)`)는 지금 구조에 안 맞음.
  전량 방식(`savePrompts(list)`)으로 확정

진짜 비용은 **읽기 쪽 한 곳**에 몰려 있었다. 초기화가 값을 받아 전역에 대입하고
그 뒤 렌더링이 이어지는 구간 — 여기만 `async`/`await` 로 바꾸면 된다.

### 4.5 단계를 쪼갠다

```
인터페이스 정의  →  호출부 교체  →  기존 함수 제거
```

정의 단계에서는 **기존 함수를 한 글자도 건드리지 않는다.** 호출부가 없으니 앱 동작이
지금과 완전히 동일해야 하고, 그게 곧 "아무것도 안 깨졌다"는 증명이 된다.
새 코드는 브라우저에서 별도로 단위 검증한다 (30개 케이스: 왕복 / 3상태 / 실패 경로 /
쓰기 차단 / 복구).

## 5. 환경 함정

### 5.1 `.gitattributes` 로 줄바꿈을 고정한다

`core.autocrlf=true` 인 Windows에서 `git add` 시 경고가 뜬다.
저장소에는 LF로 들어가지만, **다시 clone하면 워킹 파일이 CRLF** 가 되어 원본 대조가 깨진다.

```
* text=auto eol=lf
*.png binary
```

적용 후 `git add --renormalize .` 로 기존 파일에 변화가 없는지 확인한다.
`git ls-files --eol` 로 `i/lf w/lf` 를 눈으로 볼 것.

### 5.2 PowerShell here-string 을 Bash에 쓰지 말 것

`@'...'@` 는 PowerShell 문법이다. Bash 툴에 넣으면 `@` 가 문자 그대로 들어가
커밋 메시지 첫 줄이 `@` 가 된다. 실제로 한 번 당했고 push 전 `--amend` 로 고쳤다.

Bash에서 여러 줄 메시지는 **heredoc + `git commit -F`**:

```bash
cat > msg.txt <<'EOF'
제목

본문
EOF
git commit -F msg.txt
```

heredoc 안에 따옴표·백틱이 많은 코드를 넣으면 파싱이 깨지기도 한다.
그럴 땐 파일을 직접 쓰는 편이 안전하다.

### 5.3 `\n` `\t` 가 문서에 실제 줄바꿈으로 박히는 사고

스크립트로 문서를 생성할 때, 문서 안에 들어갈 **코드 예제의 이스케이프**가
한 번 더 해석돼 실제 줄바꿈/탭이 되어 코드가 깨진 채 저장됐다.

→ **문서에 넣은 코드는 문서에서 다시 뽑아 실행해 본다.** `sed` 로 코드블록을 추출해
돌려보면 즉시 드러난다.

### 5.4 ★ "초기화 완료" 로그는 검증 근거가 아니다

인라인 `<script>` 최상위의 `console.log('... 완료 ✅')` 는 **파싱 시점에 즉시** 출력된다.
`DOMContentLoaded` 초기화보다 **먼저** 찍힌다.

→ 콘솔에 "완료"가 보여도 초기화가 성공했다는 뜻이 아니다. 초기화가 첫 줄에서 터져도
그 로그는 그대로 찍힌다. **동작 확인은 화면과 실제 조작으로 한다.**

### 5.5 헤드리스 브라우저로 실제 검증하기

`node --check` 는 구문만 본다. 동작은 진짜 브라우저로 확인한다.

```bash
chrome.exe --headless=new --disable-gpu --no-sandbox \
  --virtual-time-budget=8000 --user-data-dir=<임시> \
  --dump-dom "file:///.../index.html" | grep -o '<div id="RESULT">[^<]*</div>'
```

프로브 스크립트를 임시 사본에 주입해 결과를 DOM에 써넣고 `--dump-dom` 으로 회수한다.
`window.addEventListener('error', ...)` 로 미처리 예외를 세면 "예외 0건"을 증명할 수 있다.
`alert` 은 가로채 기록만 하도록 덮어써야 멈추지 않는다.

### 5.6 `CLAUDE.md` 는 저장소 루트에 둔다

세션 시작 시 자동으로 읽히는 위치다. 하위 폴더에 두면 로드되지 않는다.

### 5.7 붙여넣기 허용 설정

긴 텍스트를 터미널에 붙여넣을 때 클라이언트가 확인을 요구할 수 있다.
계획서·프롬프트처럼 긴 입력을 자주 넣는 작업에서는 미리 허용해두면 흐름이 끊기지 않는다.

## 6. 검수 배치 — 기계는 매 단계, 사람은 분기점에

**기계 검증은 매 단계 전부 돌린다.** 싸고 빠르다.
`fnmap` 대조 → 개수 → `node --check` → 전 파일 이어붙여 중복 선언 검사 → 헤드리스 실행.

**사람(Codex) 검수는 분기점에 배치한다.** 매 커밋마다 부르면 비용만 든다.
실제로 사람 검수가 잡아낸 것은 기계가 절대 못 잡는 종류였다:

- `DOMContentLoaded` 병합으로 **예외 격리가 사라진 것** (§3) — 구문·해시 전부 통과했다
- 계획서의 **사실 오류** (`renderCategoryDropdown` 에 있지도 않은 호출을 지우라는 지시)
- **개수 검증의 상쇄 맹점** (§2.1)
- "호이스팅이라 안전하다"는 **틀린 근거** (§1.2)

→ 기계는 "바뀌었는가"를 보고, 사람은 "이 설계가 맞는가"를 본다. 역할이 다르다.
그리고 **검수에서 나온 지적은 코드뿐 아니라 계획서에도 반영**해야 같은 실수가 반복되지 않는다.
