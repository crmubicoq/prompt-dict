# T-104 · 일괄 붙여넣기 설계

> P1의 핵심이자 **D1(실데이터 수집)의 유일한 통로.**
> 메모장 · 카톡 · LLM 대화기록에 흩어진 프롬프트 150개 이상을 옮긴다.
> 코드 착수 전 설계. 결정과 근거를 함께 적는다.

**완료 조건 (TODO.md)** — 메모장 텍스트를 붙여넣어 **10개 이상 한 번에 등록.**

---

## 0. 설계 원칙

이 기능은 **한 번 크게 쓰고 그 뒤로는 거의 안 쓴다.** D1 동안 150개를 넣고 나면
단건 등록이 주 경로가 된다. 그래서 두 가지를 우선한다.

1. **틀리게 쪼갠 것을 사용자가 즉시 알아챌 수 있어야 한다.**
   150개를 잘못 넣으면 되돌리는 비용이 넣는 비용보다 크다.
2. **똑똑함보다 예측 가능성.** 자동 감지로 알아서 해주는 것보다,
   무엇이 어떻게 쪼개졌는지 숫자로 보여주고 사용자가 고르게 한다.
   → [decisions §11](./decisions/2026-09-08.md) "규칙은 단순할수록 낫다"

`content` 는 **어떤 경우에도 자동 변형하지 않는다.** 분할과 trim 외에는 손대지 않는다.
(CLAUDE.md 절대 금지)

## 1. 진입점

### 결정 — 별도 모달. 진입점은 기존 추가 버튼 옆

```html
<!-- index.html:102 기존 버튼 행 -->
<div style="display: flex; gap: 12px;">
    <button id="add-prompt-btn" style="flex: 1;">+ 새 프롬프트 추가</button>
    <button id="bulk-paste-btn" ...>📋 여러 개 붙여넣기</button>   <!-- 신규 -->
    <button id="toggle-selection-mode-btn" ...>✓ 선택 모드</button>
</div>
```

### 근거

**기존 추가 모달에 탭으로 넣지 않는다.**

- 두 화면의 성격이 다르다. 단건은 **폼**, 일괄은 **N행 미리보기 테이블**이다.
  한 모달에 넣으면 `form.reset()` · 네이티브 검증 · `closeModal` 의 "작성 중" 확인이
  두 모드에서 다르게 동작해야 한다. T-101 결함이 정확히 그 종류의 문제였다
- **T-102에서 추가 모달을 최소 입력으로 깎아냈다.** 거기에 탭을 얹으면 되돌리는 셈이다
- 일괄은 D1 한정 도구다. 상시 경로에 복잡도를 더할 이유가 없다

**사이드바 업로드 영역 옆이 아니라 메인의 추가 버튼 옆에 두는 이유** —
사이드바 업로드는 *파일*, 이건 *붙여넣기*다. 사용자 머릿속에서는
"프롬프트를 추가한다"가 같은 묶음이고, 추가 버튼 옆이 D1 동안 가장 눈에 띈다.

### 대안 (기각)

| 대안 | 기각 이유 |
|---|---|
| 추가 모달 안 탭 | 위 참조 |
| 사이드바 업로드 영역에 통합 | 파일 드래그와 붙여넣기가 한 UI에 섞이면 무엇이 일어날지 예측이 어렵다 |
| 별도 페이지 | SPA 아님. 라우팅 도입은 과함 |

## 2. 구분자

### 실제 소스의 형태

| 소스 | 형태 | 구분자 기반 분할 |
|---|---|---|
| 메모장 | 프롬프트 사이 빈 줄 1~2개, 때로 `---` 나 번호 | **잘 맞음** |
| LLM 대화기록 | `You:` / `ChatGPT:` 또는 마크다운 `##` | 부분적 |
| 카톡 내보내기 | `[이름] [오후 3:24] 메시지` 가 줄마다 | **잘 안 맞음** |

카톡은 정직하게 인정한다. 한 프롬프트가 여러 메시지에 걸쳐 있고 타임스탬프가 섞인다.
**구분자로는 못 쪼갠다.** 대응: **"나누지 않음"** 으로 통째로 넣고 미리보기에서 본문을 다듬거나,
붙여넣기 전에 메모장에서 대충 정리한다. 자동 병합 기능은 범위 밖(P2 후보).

### 결정 — 옵션 5개 + **모든 옵션의 분할 개수를 동시에 표시**

```
구분자   ○ 빈 줄 2개 (23개)   ○ ---  (1개)   ○ ===  (1개)   ○ 직접 입력 [____] (—)
         ○ 나누지 않음 (1개)
```

- **기본값: 빈 줄 2개.** 메모장 소스에서 가장 흔하다
- **자동 감지로 기본값을 바꾸지 않는다.** "가장 많이 쪼개지는 것"을 고르면
  잘못 쪼갤 때 사용자가 눈치채기 어렵다. 항상 같은 것에서 출발해야 이상함을 알아챈다
- **개수는 전부 실시간 표시.** 이게 자동 감지를 대체한다 —
  `빈 줄 2개 (1개)` 가 보이면 사용자가 즉시 다른 걸 고른다
- **빈 줄 1개는 옵션에서 뺀다.** 프롬프트 본문 안의 문단 구분과 구별되지 않아
  거의 항상 과도하게 쪼갠다

### 분할 규칙

```
빈 줄 2개   /\n\s*\n\s*\n/     (\r\n 정규화 후)
---         /^\s*-{3,}\s*$/m   줄 전체가 하이픈일 때만
===         /^\s*={3,}\s*$/m   줄 전체가 등호일 때만
직접 입력    사용자 문자열. 줄 전체 일치가 아니라 단순 분할
나누지 않음  분할 없음
```

각 조각은 `trim()` 후 **빈 것 제거**. 그 외 변형 없음.

## 3. 미리보기 UI

### 레이아웃

```
┌─ 📋 여러 개 붙여넣기 ───────────────────────────────── ✕ ─┐
│                                                            │
│  [ 텍스트 붙여넣기 textarea · rows=8 ]                     │
│                                                            │
│  구분자  ○ 빈 줄 2개 (23)  ○ --- (1)  ○ === (1)            │
│          ○ 직접 입력 [___]  ○ 나누지 않음 (1)              │
│  ─────────────────────────────────────────────────────    │
│  23개 중 21개 선택 · ⚠ 짧음 2 · ⚠ 중복 의심 1              │
│  [전체 선택] [전체 해제]   카테고리 [미분류 ▾]  [✨ AI 자동정리 (P4)] │
│  ─────────────────────────────────────────────────────    │
│  ☑ ① [제목 입력란_______________]  본문 320자   ⌄          │
│  ☑ ② [제목 입력란_______________]  본문 88자    ⌄          │
│  ☐ ③ [제목 입력란_______________]  ⚠ 12자       ⌄          │
│  ☐ ④ [제목 입력란_______________]  ⚠ 중복       ⌄          │
│  ...                                                       │
│  ─────────────────────────────────────────────────────    │
│                      [ 취소 ]  [ 21개 등록 ]               │
└────────────────────────────────────────────────────────────┘
```

### 조각마다 보여주는 것

| 요소 | 설명 |
|---|---|
| 체크박스 | 포함/제외. 기본 체크, 경고 항목은 기본 해제 |
| 번호 | 원본 순서 |
| 제목 입력란 | `suggestTitle(chunk)` 로 **value 를 미리 채운다** |
| 본문 요약 | 첫 줄 + 글자수. `⌄` 로 펼치면 편집 가능한 textarea |
| 경고 배지 | 짧음 / 김 / 중복 |

### ★ 제목을 `placeholder` 가 아니라 `value` 로 채우는 이유

T-103 단건 폼에서는 `placeholder` 를 택했다([decisions §11](./decisions/2026-09-08.md)).
**여기서는 반대로 간다.** 맥락이 다르기 때문이다.

| | 단건 폼 | 일괄 미리보기 |
|---|---|---|
| 사용자 의도 | 제목을 직접 쓸 수도 있다 | 150개를 직접 쓰지 않는다. 대부분 그대로 쓰고 몇 개만 고친다 |
| `value` 로 채우면 | 직접 쓰려면 **지워야 해서** 마찰이 는다 | 그대로 두면 되므로 마찰이 없다 |
| `placeholder` 로 두면 | 방해하지 않는다 | **23행이 전부 회색 텍스트**라 실제 값과 구분이 안 되고, 무엇이 저장될지 스캔이 어렵다 |

같은 원칙("사용자를 방해하지 않는다")에서 서로 다른 결론이 나온다.
설계를 베끼지 말고 이유를 봐야 하는 사례라 기록해둔다.

### 개별 수정 범위 — 제목 + 본문 둘 다

본문 수정이 필요한 실제 사례: 카톡 덩어리에서 앞의 `[이름] [오후 3:24]` 줄을 지우는 것.
다만 **기본은 접힘.** 펼칠 때만 `textarea` 를 생성한다(아래 성능 참조).

### 조각이 많을 때

150개까지는 **전 행을 렌더한다.** 다만:

- 각 행은 **제목 `<input>` 하나만** 갖는다. 본문 `textarea` 는 펼칠 때 생성
- 가상 스크롤은 쓰지 않는다 — P2 T-202의 주제이고, 150행 정도는 부담이 아니다
- 200개를 넘으면 상단에 `조각이 200개를 넘습니다. 나눠서 등록하는 것을 권합니다` 안내
  (막지는 않는다)

### 경고 기준

| 배지 | 기준 | 기본 체크 |
|---|---|---|
| ⚠ 짧음 | 본문 20자 미만 | **해제** |
| ⚠ 김 | 본문 5,000자 초과 | 유지 |
| ⚠ 중복 | 기존 프롬프트 또는 다른 조각과 본문 일치 | **해제** |

짧은 조각은 구분자를 잘못 골랐을 때 대량으로 생긴다. 기본 해제가 안전하다.
긴 조각은 쪼개기에 실패했을 신호지만 정당한 긴 프롬프트일 수도 있어 유지한다.

## 4. 저장

### 결정 — `savePrompts` 1회 + 스냅샷 롤백

```js
const snapshotPrompts = [...allPrompts];
selected.forEach(chunk => allPrompts.unshift(buildPrompt(chunk)));

if (await PromptStorage.savePrompts(allPrompts) !== true) {
    allPrompts = snapshotPrompts;
    applyFilters();
    showToast('저장 실패 — 등록을 되돌렸습니다 ❌');
    return;
}
```

**부분 성공을 허용하지 않는다.** 전량 저장 후 실패하면 전부 롤백한다.
근거: 어댑터가 컬렉션을 통째로 쓰므로 애초에 부분 저장이 불가능하고,
"21개 중 13개만 들어갔다"는 상태는 사용자가 수습할 수 없다.
→ [devlog §4.8](./devlog.md)

즐겨찾기는 바뀌지 않으므로 `savePrompts` 만 부른다.
→ [decisions §5](./decisions/2026-09-08.md) "필요한 것만 저장"

### 카테고리 — 기본 미분류 + 일괄 지정 옵션

상단 툴바에 드롭다운 하나. **기본값 미분류**, 선택하면 이번 등록분 전체에 적용된다.
한 번에 붙여넣는 덩어리는 대개 한 주제라 유용하고, 안 쓰면 그냥 미분류로 간다.
개별 조각의 카테고리 지정은 넣지 않는다 — 그건 T-105(일괄 분류 UI)의 일이다.

### 중복 감지

**본문 정규화 후 완전 일치**만 본다.

```js
const norm = s => s.replace(/\s+/g, ' ').trim();
```

- 기존 `allPrompts` 와 비교, 그리고 조각끼리도 비교
- 유사도(편집 거리 등)는 **쓰지 않는다.** 오탐 비용이 크고
  클라이언트 연산 제약(CLAUDE.md)에도 맞지 않는다
- 감지된 조각은 배지 + 기본 체크 해제. **막지는 않는다** — 의도적 중복일 수 있다

### ★ 불러오기 카테고리 기본값 — `기타` → `미분류` 로 바꾼다

T-101에서 미뤘던 결정([decisions §14](./decisions/2026-09-08.md)). **바꾼다.**

현재 [`validateCategory`](../js/categories.js) 는 이렇다.

```js
if (!category) return '기타';                       // ← 미분류로
const exists = categories.some(c => c.name === category);
return exists ? category : '기타';                  // ← 미분류로
```

**근거는 decisions §10과 정확히 같다.** `기타` = 골라서 넣은 것, `미분류` = 아직 안 고른 것.
파일에서 들어온 항목은 **아무도 고르지 않았다.** `기타`로 보내면
T-105 정리 대상에서 빠지고, 150개 이관의 핵심인 그 구분이 무너진다.

없는 카테고리 이름(예: 파일에 `"마케팅"`)도 마찬가지다. 사용자가 그 이름을 골랐지만
이 시스템에는 없다 — 재분류가 필요한 상태이므로 `미분류` 가 맞다.

**함께 바뀌는 것**

- `import.js` 3곳의 `defaultCategoryCount` 메시지: `'기타'로 분류됨` → `'미분류'로 분류됨`
- `parseTXTFile` 의 하드코딩 `category: '기타'` → `UNCATEGORIZED`
- **`deleteCategory` 의 "소속 프롬프트를 기타로 이동"은 유지한다.**
  그건 사용자가 이미 분류했던 것이고, 미분류로 되돌리면 정보를 잃는다
  ([decisions §10](./decisions/2026-09-08.md)에서 확정)

**위험:** 기존 동작 변경. 다만 실데이터 0건이라 지금이 가장 싸다.

## 5. AI 자동정리 버튼 자리

[decisions 2026-09-07 §5](./decisions/2026-09-07.md) 방침 그대로:
**P1에서는 미리보기 화면을 제대로 만들고 버튼 자리만 비워둔다.**

```html
<button type="button" id="ai-organize-btn" disabled
        title="P4에서 연결됩니다. 제목·카테고리·태그를 자동으로 제안합니다. 본문은 수정하지 않습니다.">
    ✨ AI 자동정리 (P4)
</button>
```

- **위치:** 미리보기 상단 툴바, "카테고리 일괄 지정" 오른쪽
- **비활성** + `title` 로 무엇을 할 것인지 설명
- P4에서 연결될 때 **이 화면은 그대로 두고 값을 채우는 방식만 교체**한다.
  그래서 미리보기 행은 "제목·카테고리·태그를 나중에 채워 넣을 수 있는" 구조여야 한다
- 본문은 절대 건드리지 않는다. 자동정리는 메타데이터 전용

## 6. 재사용

### `suggestTitle(content)` — 그대로 쓴다

T-103에서 순수 함수로 만들어뒀다. 조각마다 호출한다. 추가 작업 없음.

### 기존 임포트 파서와 겹치는 부분

`parseTXTFile` 이 이미 텍스트를 쪼갠다. **겹치지만 규칙이 다르다.**

| | `parseTXTFile` | T-104 |
|---|---|---|
| 구분자 | `---` 고정 | 선택 |
| 제목 | **첫 줄** | `suggestTitle()` |
| 본문 | 첫 줄 **제외**한 나머지 | **전체** |
| 미리보기 | 없음 (바로 저장) | 있음 |

제목·본문 규칙이 정반대다. `parseTXTFile` 은 "첫 줄이 제목"이라는 형식을 전제하고,
T-104는 그런 전제 없이 아무 텍스트나 받는다.

### 결정 — 분할 함수만 공유, 파서는 지금 건드리지 않는다

```js
// js/bulk.js
function splitChunks(text, delimiter) { ... }   // 순수 함수, 재사용 가능
```

- `splitChunks` 는 **순수 함수로 만들되, `parseTXTFile` 을 지금 바꾸지 않는다.**
  T-104 범위를 키우지 않기 위해서다
- `parseTXTFile` 은 **T-121**(TXT 구분자 `---` → `===PROMPT===`)에서 어차피 손댄다.
  그때 `splitChunks` 를 쓰게 하고, 제목 규칙도 통일할지 함께 결정한다
- 저장 로직은 `handleFormSubmit` 과 패턴만 같고 코드는 공유하지 않는다
  (단건 vs N건, 폼 검증 유무)

### 파일 배치 — 새 파일 `js/bulk.js`

- `import.js` 는 **파일 업로드 파서** 전용이고 이미 262줄이다. T-104는 그보다 커진다
- `<script>` 순서: `import.js` 다음, `main.js` 앞
- 3원칙 준수 — 함수 선언만, 초기화 호출은 `main.js` 에서
  ([devlog §1.3](./devlog.md))

## 10. 확정된 결정 (열린 질문 → 답)

착수 전 GON 확인이 필요했던 3건. **전부 확정됐다.**

### 10.1 "나누지 않음" 옵션 — **넣는다**

카톡 대응 경로가 이것뿐이다. 구분자로 못 쪼개는 덩어리를 통째로 받아
미리보기에서 다듬는 흐름이 유일한 대안이다.

단건 폼과 겹친다는 우려가 있었지만, **붙여넣기 화면까지 온 사용자를
단건 폼으로 돌려보내는 것이 더 큰 마찰이다.** 기능이 겹치는 비용보다
경로가 끊기는 비용이 크다.

### 10.2 200개 초과 — **막지 않고 경고**

```
⚠ 조각이 247개입니다. 구분자를 잘못 고르셨을 수 있습니다.
   각 조각의 길이를 확인해 주세요.
```

- **"구분자를 잘못 고르셨을 수 있습니다"를 명시적으로 쓴다.** 개수만 보여주면
  사용자가 원인을 짐작해야 한다. 실제 원인 1순위를 문장으로 지목한다
- **막지 않는다.** 전량 롤백이 있어 실수해도 복구된다(§4).
  막으면 정당한 대량 입력까지 막힌다

### 10.3 등록 후 — **모달 유지, 입력창만 비움**

소스가 3종(메모장 · 카톡 · LLM 대화기록)이라 **이어서 넣을 가능성이 높다.**
매번 닫고 다시 여는 것은 D1 내내 반복되는 마찰이다.

- `textarea` 와 미리보기 목록만 비운다
- 구분자 선택과 카테고리 일괄 지정은 **유지한다** (같은 소스를 이어 넣을 때 유용)
- 상단에 **누적 표시**를 둔다 — `이번 세션 34개 등록`
- 닫기는 사용자가 ✕ 또는 취소로

## 11. 착수 순서

### **T-111 · T-112 · T-113 → T-104**

T-104를 먼저 하지 않는다. 근거 둘:

1. **T-104는 외부 텍스트 150개를 들여오는 관문이다.**
   메모장 · 카톡 · LLM 기록에 `<` 나 `'` 가 섞일 확률이 낮지 않은데,
   `createPromptCard` 는 아직 이스케이프하지 않는다.
   B2(태그에 `'` 가 있으면 인라인 `onclick` 이 깨짐)는 이미 실버그다.
2. **셋 다 `createPromptCard` 를 건드린다.** 순서를 뒤집으면 같은 함수를 두 번 고친다.
   T-113(이벤트 위임)은 T-112(XSS)와 한 묶음이라는 것도 이미 정리돼 있다
   ([decisions 09-08 §4](./decisions/2026-09-08.md)).

| 순서 | 태스크 | 내용 |
|---|---|---|
| 1 | T-111 | `escapeHtml()` 유틸 (적용은 T-112) |
| 2 | T-112 | `createPromptCard` 전 필드 이스케이프 |
| 3 | T-113 | 인라인 `onclick` → 이벤트 위임 (+ F3 인덱스 → id 기반) |
| 4 | **T-104** | 일괄 붙여넣기 (본 문서) |

T-113에서 인덱스 기반 식별자(검수 F3)와 `setTimeout(0)` 원인 토스트도 함께 정리한다
([decisions 09-08 §14](./decisions/2026-09-08.md)).
