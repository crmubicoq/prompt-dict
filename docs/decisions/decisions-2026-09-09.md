## 3. "미분류"를 "기타"와 합치지 않은 이유 (T-101)

기타를 재사용하면 코드가 줄지만 나눴다.

1. **기타는 사용자가 삭제·수정할 수 있는 일반 카테고리다.** 지우면 미분류
   프롬프트가 사이드바에서 통째로 사라진다
2. **의미가 다르다.** 기타 = 골라서 넣은 것, 미분류 = 아직 안 고른 것.
   합치면 T-105에서 **정리할 대상을 골라낼 수 없다.** 150개 이관의 핵심이
   바로 그 구분이다
3. 카테고리 삭제 시 소속 프롬프트가 기타로 가는 기존 동작과 충돌하지 않는다

구현은 `categories` 배열 **밖의 특수 값**. 관리 화면에 나타나지 않아
삭제·수정이 불가능하다.

이 결정이 나중에 세 곳에서 값을 냈다 — T-104f(불러오기 폴백),
T-105(정리 대상 식별), T-114(임포트 시 미분류 걸러내기).

## 4. 제목 자동 제안 — 단건은 placeholder, 일괄은 value (T-103 / T-104c)

**같은 원칙에서 반대 결론이 나온 사례.**

| | 단건 폼 | 일괄 미리보기 |
|---|---|---|
| 사용자 의도 | 직접 쓸 수도 있다 | 150개를 직접 쓰지 않는다 |
| `value` | 지워야 해서 마찰 ↑ | 그대로 두면 됨 |
| `placeholder` | 방해 안 함 | 23행이 전부 회색이라 실제 값과 구분 불가 |

**역할 지정("너는 ~로서")은 패턴 감지 없이 그대로 제목으로 쓴다.**
감지해서 건너뛰면 동작이 예측 불가능해지고 정보량이 가장 많은 줄을 버릴
위험이 있다. 어차피 제안이고 사용자가 고친다. **규칙은 단순할수록 낫다.**

## 6. escapeHtml — 두 한계를 인정하고 넘어갔다 (T-111 / T-112)

### 이중 이스케이프는 의도된 동작
멱등성을 넣으면 정직하게 `&amp;` 를 타이핑한 사용자의 글자가 `&` 로
둔갑한다. **조용한 데이터 변조**라 원문 보존 원칙과 충돌한다.
→ 규칙: **텍스트가 HTML로 들어가는 경계에서 정확히 1회만 호출**

### ★ 인라인 onclick 은 이스케이프로 못 막는다
HTML 파서가 `&#39;` 를 `'` 로 되돌린 **다음** 그 결과를 JS로 파싱한다.
헤드리스로 실측해 확인했다 — 이스케이프하고도 주입이 실행됐다.

**어설프게 감싸면 "막았다"는 착각만 남는다.** 그래서 T-112에서 손대지 않고
주석으로 표시만 했고, T-113(이벤트 위임)에서 구조적으로 해결했다.

`B1`을 "T-112에서 닫혔다"고 뭉뚱그렸으면 T-113을 미룰 명분이 됐을 것이다.

### `<img>` 의 javascript: 는 실행되지 않는다 (내 오해 정정)
`<img>` 는 브라우징 컨텍스트를 만들지 않아 스킴이 무해하다. 실측으로 확인.
그럼에도 화이트리스트를 넣은 이유는 **임포트로 들어온 값이 저장돼
다른 문맥(CSS background, object, export 후 타 앱)으로 옮겨갈 때** 위험하기
때문이다.

## 7. T-104 설계 판단들

### 구분자 — 자동 감지 대신 전 옵션 개수 동시 표시
"가장 많이 쪼개지는 것"을 자동 선택하면 **잘못 쪼갤 때 눈치채기 어렵다.**
항상 같은 데서 출발해야 이상함이 보인다. 기본값은 빈 줄 2개 고정.

빈 줄 1개는 옵션에서 뺐다 — 본문 문단 구분과 구별되지 않아 거의 항상
과분할한다.

**카톡은 구분자로 못 쪼갠다고 정직하게 적었다.** 한 프롬프트가 여러 메시지에
걸치고 타임스탬프가 섞인다. 대응은 "나누지 않음" + 본문 편집.
억지로 규칙을 만들지 않았다.

### 진입점 — 별도 모달. 기존 추가 폼에 탭으로 넣지 않는다
단건은 폼, 일괄은 N행 테이블이라 `form.reset()`·네이티브 검증·"작성 중"
확인이 모드마다 갈라져야 한다. **T-101 결함이 정확히 그 종류였다.**
T-102에서 폼을 최소로 깎았는데 탭을 얹으면 되돌리는 셈이기도 하다.

### 경고 4종의 기본 체크 — 비용 비대칭
| 배지 | 기본 | 근거 |
|---|---|---|
| 짧음(20자↓) | **해제** | 구분자 실수로 **대량 발생**. 잘못 등록하면 쓰레기 정리 비용이 크다 |
| 김(5000자↑) | **유지** | 정당하게 긴 프롬프트가 있고 대량 발생하지 않는다. 해제하면 넣으려던 내용이 조용히 빠진다 |
| 기존과 중복 | 해제 | 같은 소스를 두 번 붙여넣는 것이 가장 흔한 원인 |
| 조각 내 중복 | 2번째부터 해제 | 둘 다 해제하면 내용이 통째로 사라져 사용자가 되살려야 한다 |

같은 "경고"인데 **반대 방향으로 처리**하는 것이 핵심이다.

### 구분자 변경 시 편집 보존은 원리상 불가능
조각 경계가 달라지면 "같은 조각"이라는 개념 자체가 성립하지 않는다.
매칭으로 보존하려 했으면 엉뚱한 조각에 편집이 붙었을 것이다.

→ 보존하지 않되 **조용히 버리지 않는다.** 확인을 받고, 거부하면 라디오도
되돌려 화면과 입력칸이 어긋나지 않게 한다.

### 200개 초과 — 막지 않고 경고
"구분자를 잘못 고르셨을 수 있습니다"를 명시적으로. 전량 롤백이 있어
실수해도 복구된다. **막으면 정당한 대량 입력까지 막힌다.**

### 등록 후 모달 유지
소스가 3종이라 이어서 넣을 가능성이 높다. textarea만 비우고
"이번 세션 N개 등록" 누적 표시.

### "나누지 않음" 옵션은 넣는다
단건 폼과 겹치지만 **카톡 대응 경로가 이것뿐**이다. 붙여넣기 화면에 온
사용자를 단건 폼으로 돌려보내는 것이 더 큰 마찰이다.

## 8. T-105 — A안 채택 (필터·검색어 변경 시 선택 비움)

**기존 동작 변경이 걸렸지만 이건 동작이 아니라 결함이다.**
"필터를 바꿨는데 안 보이는 25개가 선택된 채로 남아 있다"를 의도된 동작으로
볼 수 없다.

**일괄 삭제 쪽이 더 위험하다** — 분류는 재분류하면 되지만 삭제는 안 보이는
것이 사라진다. 그래서 함께 고쳤다.

B안(확인 문구 개수로만 걸러내기)은 **숫자를 읽어야 알아채는** 방식이라
반복 작업에서 놓친다. 30번쯤 하면 확인 문구를 안 읽게 된다.
C안(보이는 것에만 적용)은 사용자가 한 선택을 조용히 무시하는 것이다.

### 삭제와 분류를 같은 UI에 두되 물리적으로 분리
분류는 D1 내내 반복되는 일상 동작, 삭제는 되돌릴 수 없는 동작.
왼쪽 그룹에 [카테고리 ▾][지정], 오른쪽에 빨간 [선택 삭제].
**반복 작업에 익숙해진 손이 옆 버튼을 누르는 것**이 위험이다.

### 분류에 확인 1번
재분류가 가능하니 불필요해 보이지만, **이 동작은 미분류 표시 자체를 지운다.**
잘못 지정하면 어떤 것이 원래 미분류였는지 복원할 방법이 없다 —
T-101이 만든 구분이 그 자리에서 사라진다. 2번은 확인 피로만 쌓인다.

### 새 목록을 만들지 않는다
카드가 크다는 것은 맞지만 실제 분류는 "150개를 하나씩"이 아니라
**주제 덩어리 단위**다 (미분류 필터 → 검색 → 전체 선택 → 지정 → 다음 키워드).
써보고 훑기가 실제로 괴로우면 그때 압축 모드를 얹는 편이, 지금 두 번째
렌더러를 만들어 두 곳을 유지하는 것보다 싸다.

## 9. T-114 — 버전이 아니라 필드 존재로 분기

`version` 문자열을 믿고 분기하는 대신 `Array.isArray(data.categories)` 로
판단한다. v1.0 파일에는 그 필드가 없으니 해당 단계가 저절로 건너뛰어진다.

**손으로 고친 파일이나 표기가 어긋난 파일에서도 깨지지 않고, 분기 코드가
아예 생기지 않는다.** 버전이 늘어도 손댈 게 없다.

### 카테고리는 id 가 아니라 이름으로 맞춘다
프롬프트가 `p.category === cat.name` 으로 가리킨다. id로 맞추면 이름이 같고
id가 다른 카테고리가 둘 생기고, **한 프롬프트가 두 카테고리에 동시에 걸린다.**

id를 부여한 것(T-113)은 클릭 대상 식별용이지 데이터 참조용이 아니다.

### 테마는 병합/덮어쓰기에 매핑
테마는 데이터가 아니라 기기 취향이다. 새 질문을 만들지 않고 기존 선택에 얹었다.
- 덮어쓰기 = "이 백업 상태로 되돌린다" → 테마 포함
- 병합 = "남의 프롬프트를 더한다" → 남의 파일이 내 기기 테마를 뒤집으면 안 된다

### 미아 프롬프트는 세어서 알린다
덮어쓰기로 카테고리가 사라져 어디에도 속하지 않게 된 프롬프트를
`validateCategory` 로 조용히 미분류로 바꾸지 않는다.
**불러오기가 사용자 데이터를 말없이 고치면 안 된다.**

## 10. T-115 — 손상 상태에서 exportData 를 쓰면 안 된다

내 지시가 함정이었다. "복구 흐름: 백업 내보내기 → 초기화 → 불러오기"라고
썼는데, **손상되면 초기화가 중단돼 `allPrompts` 가 비어 있다.**
내보내면 빈 백업이 나오고 **사용자는 백업했다고 믿는다.** 그 상태에서
초기화하면 원본이 영영 사라진다.

→ `rawBackup` 원본을 그대로 내려받게 한다. 파싱이 필요 없어 손상 상태에서도
항상 동작한다. 이것이 복구의 첫 단계이자 가장 중요한 동작이다 —
**사용자의 바이트를 브라우저 밖으로 꺼내는 것.**

### 순서를 UI가 강제한다
`removeAll()` 이 `rawBackup` 을 비운다. 원본 내려받기가 초기화보다 반드시
먼저여야 한다. 안 받았을 때만 경고를 하나 더 붙였다 — 받은 사람에게
불필요한 단계를 강요하지 않으면서 위험한 경로만 막는다.

### 모달이 아닌 배너
모달은 부분 손상일 때 앱을 못 쓰게 만든다. 배너는 치명적일 때(뒤가 빈 화면)
유일한 조작 대상이 된다. **두 등급을 하나로 감당한다.**

### `location.reload()`
`removeAll()` 은 저장소만 지우고 메모리는 남는다. 전역을 하나씩 리셋하면
**빠뜨린 하나가 그대로 버그가 된다.** 사용자가 확인한 의도적 동작이라
새로고침이 놀랍지 않다.

### alert → 배너 대체
같은 정보를 두 번 보여줄 이유가 없고, alert 은 초기화 도중 여러 번 뜬다.
그리고 **누르면 사라진다** — 무심코 확인을 눌렀다가 "뭐라고 떴었지" 하면
다시 볼 방법이 없다.

## 11. ★ 이미지 프롬프트 소스를 D1 2회차로 분리

테스트로 올린 PPTX(나노 바나나 템플릿 33장) 분석에서 나온 결정.

### 이미지가 부속물이 아니라 본체다
"네온 사인 스타일" 33개를 **글로만 읽고 구분하는 것은 사실상 불가능**하다.
텍스트만 먼저 넣으면 나중에 이미지를 붙이려고 33개를 하나씩 다시 열어야
하는데, 그게 지금 처음부터 하는 것보다 비싸다.

### 용량이 하드 블로커
```
이미지 33장 = 19MB → base64 26MB
localStorage 한계 5MB. 8~9장이면 꽉 찬다
```
B4(썸네일 base64)가 이론이 아니라 **실제로 막는 사례**다.
서버에서 파일 저장 + 경로 참조로 바꾼 뒤에야 가능하다.

### 그래서 소스를 두 갈래로
| 소스 | 이미지 | 처리 |
|---|---|---|
| 메모장·카톡·LLM 대화기록 | 없음 | **D1 1회차, 지금** |
| PPTX 등 이미지 프롬프트 | 필수 | **D1 2회차, P4 이후** |

D1을 통째로 미루지 않고 **이미지가 필요 없는 것부터** 넣는다.

### B4를 P1에서 손댈 이유가 없어졌다
어차피 서버 가야 해결된다. 로컬에서는 이미지 있는 프롬프트를 몇 개 이상
못 넣는다.

"기억이 선명할 때 만들어두자"고 제안했다가 철회했다. **그건 내 사정이지

  지금 만든 구조가 그때 스키마와 안 맞을 가능성이 높다
- PPTX 구조 분석은 이미 devlog §7에 남아 있다. 다시 해도 5분이다

**앱 로직이 망가질 걱정은 없었다** — 앱 코드를 전혀 안 건드리는 별도
파이썬 스크립트라서. 미룬 이유는 순전히 "지금 만들면 나중에 고친다"였다.

## 13. 이번 세션에서 반복 확인된 패턴

### 테스트가 실제 경로를 우회하면 통과해도 증명이 안 된다
T-101이 45/45 통과했는데 실제로는 안 고쳐진 상태였다.
`dispatchEvent(new Event('submit'))` 이 네이티브 폼 검증을 건너뛴 탓이다.
→ 이후 전 검증을 `form.requestSubmit()` 과 실제 클릭으로 전환.

### 조사를 먼저 하면 설계가 바뀐다
T-009 전 조사, T-104 전 설계, T-105 전 설계 — 셋 다 조사 결과가 계획을
바꿨다. 특히 T-104 조사에서 "19곳 중 프롬프트+즐겨찾기를 둘 다 저장해야
하는 곳은 3곳뿐"이 나와 원자성 문제 범위가 6분의 1로 줄었다.

### 지시 목록에 없던 것이 계속 나왔다
`parseInt` 4곳(UUID를 NaN으로), 썸네일 `onclick` 2곳,
`parseJSONFile` 의 `thumbnailImage` 누락, `renderPromptList` 의 카운트
early return, 임포트 카운터 버그, 150행에서 모달이 13,705px로 늘어난 것.

**전수 조사와 실측을 지시에 넣은 것이 매번 값을 냈다.**
