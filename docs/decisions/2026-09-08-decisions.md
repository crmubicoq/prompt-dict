## 1. 작업 방식을 로컬 기준으로 바꿨다

**이전:** VS Code Remote SSH로 팀 우분투 서버에 직접 붙어 작업
**변경:** 로컬 PC에서 작업 → GitHub → 서버에서 `git pull`

**이유:** 서버에서 바로 작업하는 게 편하긴 한데, **내부망을 못 쓰는 상황에서는
아예 작업이 안 된다.** 외부에서도 진행할 수 있어야 한다.

**따라오는 원칙:** 서버에서는 코드를 편집하지 않는다. 급하게 고칠 일이 생겨도
로컬에서 고쳐 push하고 서버에서 pull. 예전에 겪은 git divergence가 이 패턴에서 나온다.

**적용 범위:** 이 프로젝트만이 아니라 **앞으로 모든 프로젝트.**

## 2. 파일 분석에서 드러난 것들이 계획을 바꿨다

원본 HTML을 분석하면서 예상과 다른 사실 5가지가 나왔고, 그게 로드맵을 다시 쓰게 했다.

### 실데이터가 0건이었다
저장된 프롬프트 3개가 전부 코드가 자동 주입한 샘플이었다.
→ 하위 호환·ID 마이그레이션 태스크를 전부 삭제. P0/P1을 과감하게 진행 가능.

### 안 쓴 이유는 도구 문제가 아니었다
처음엔 "만들었는데 안 쓰게 된 이유"를 접근 마찰·입력 마찰·재사용 안 함 세 가지로
좁혔는데, 실제로는 **아직 시작을 안 한 것**이었다.
프롬프트가 계속 쌓이기만 하고 정리가 안 돼서 만들었고, 만든 뒤 다른 작업에 밀려
데이터를 못 넣었다.

→ 통증 3가지(못 찾음 / 공유 안 됨 / 이력 안 남음)는 가설이 아니라 실제 경험이 맞다.
"전제를 다시 보자"는 제안은 철회.

### 진짜 병목은 코드가 아니라 등록 작업이다
옮겨야 할 프롬프트가 150개 이상, 소스는 메모장 / 카톡·슬랙 / 예전 LLM 대화기록 —
**전부 비정형.** 하나씩 모달로 넣는 건 불가능하다.

→ P1의 성격을 "버그 수정"에서 **"등록 마찰 제거"** 로 바꿨다.
일괄 붙여넣기(T-104)와 카테고리 필수 해제(T-101)가 최우선이 됐다.

### 참고자료 기능은 실사용 0건이었다
`promptDictionary_references` 키가 생성조차 안 됐다.
→ 코드 400줄을 서버까지 끌고 가면 인증·소유자 격리·백업 대상에 다 포함시켜야 한다.
활성 코드에서 제외. `legacy/original.html` 과 git 히스토리에 보존되므로 복원 가능.

### CSV 임포트는 우선순위를 두 번 뒤집었다
처음엔 "대량 입력의 유일한 통로인데 고장나 있다"며 P1 필수로 올렸다가,
소스에 엑셀이 없다는 걸 확인하고 다시 후순위로 내렸다.
메모장·카톡·대화기록은 CSV로 만들 수 없는 형태고, 억지로 옮기는 것 자체가 노동이다.

→ 필요한 건 **텍스트 덩어리를 그대로 붙여넣고 쪼개는 경로.**

## 3. 기존 도구를 쓰지 않고 직접 만들기로 했다

`prompts.chat`(GitHub 스타 143k)이 기능상 상위호환이다. 자체 호스팅 가능하고,
버전 관리·변수 치환·시맨틱 검색·카테고리·태그가 이미 다 있다.

**제외 사유 — 서버 사양.**
PostgreSQL + Node 24 + Next.js SSR + OAuth가 필요하다. 팀 서버는 사양이 넉넉하지 않고
이미 서비스 7개가 돌고 있다. slide-motion P4를 서버 성능 때문에 미룬 것보다 더 무겁다.
거기에 한국어 미지원, 투표·리더보드 등 불필요 기능 다수.

**Tae4an/mcp-prompt-manager** 는 P2 기능 목록과 거의 일치하지만, Claude Code 안에서
쓰는 개인용 도구라 팀원 5명이 브라우저로 공유하는 용도가 아니다.

### 조사에서 가져온 것
- 버전 diff 표시 → P2 버전 이력에 포함
- 변수 치환이 사실상 표준 기능임을 확인 → 후순위에서 중위로 상향

### 어느 도구에도 없어서 우리만 갖는 것
1. **일괄 붙여넣기** — 카톡·LLM 대화 덩어리를 그대로 등록.
   다들 "잘 정리된 프롬프트를 하나씩 입력한다"를 전제한다
2. **한글 초성 검색** (`ㅍㄹㅍㅌ` → 프롬프트) — 전부 영어권 도구라 미지원
3. 기존 팀 허브·인증과 동일한 접근 경로

## 4. 성능 원칙 — 연산은 전부 브라우저에서

서버 사양 제약에서 나온 결론. 프롬프트 150개 ≈ 300KB.
**접속 시 전체를 한 번 내려받고** 검색·필터·정렬·diff·초성변환을 클라이언트에서 처리.
서버는 저장 / 불러오기 / 인증만 담당. 500개까지 이 구조가 유지된다.

**금지:** 임베딩 기반 시맨틱 검색, SSR 프레임워크, PostgreSQL, 상시 백그라운드 작업

## 5. AI 자동정리는 앱의 핵심 기능이지만 P4 이후로 미룬다

프롬프트 본문만 붙여넣으면 제목·카테고리·태그·설명이 자동으로 채워지는 흐름.
P-4(등록 마찰)를 정면으로 푸는 것이라 **부가 기능이 아니라 핵심**이다.

### 미루는 이유
브라우저에서 API 키를 직접 쓸 수 없다(file-transformer 때와 같은 문제).
LiteLLM 프록시를 거쳐야 하므로 **서버 단계에서만 가능**하다.
그리고 실제로 써보기 전에 세부 설계를 확정하면 그때 가서 또 바뀐다.

### 확정한 것
- **결과는 반드시 사람이 확인 후 저장.** 자동 저장하지 않는다
- **본문은 절대 수정하지 않는다.** 메타데이터만 생성.
  프롬프트는 한 글자가 결과를 바꾸므로 "정리"하면 잘 작동하던 게 망가진다
- 단건 등록과 일괄 등록이 **같은 엔진**을 쓴다 (입력 개수만 다름)
- 덩어리 분할은 AI가 아니라 **규칙 기반으로.** 150개를 통째로 던지면
  누락·병합이 조용히 일어난다
- **P1에서는 미리보기 화면을 제대로 만들고 자동정리 버튼 자리만 비워둔다.**
  나중에 화면은 그대로 두고 값 채우는 방식만 교체

### 별도 하베스터 스킬은 만들지 않는다
처음엔 이관 전용 도구를 따로 만들자고 했는데, 같은 자동정리를 여러 개에
적용하면 그게 이관 기능이다. 하나 만들면 둘 다 해결된다. → 취소.

## 6. 어댑터 설계 판단

### 전량 방식으로
계획서 최초안은 `savePrompt(p)` 단건 API였으나, 조사 결과 실제 코드는 전부
컬렉션 통째 저장이었다. 단건 API로 가려면 코드를 대폭 고쳐야 하고 그건 리팩터링
범위를 벗어난다. → `getPrompts()` / `savePrompts(list)`. 단건은 P3에서 필요하면 추가.

### 객체명 `Storage` → `PromptStorage`
`Storage` 는 브라우저 내장 인터페이스 이름이다. 지금은 `instanceof Storage` 사용이
0건이라 무해하지만, P3에서 라이브러리를 붙이면 충돌할 수 있다.
**이름 바꾸는 비용이 지금은 0, 나중엔 호출부 전체.** 문서 표기도 함께 옮겼다.

### 원자성 문제는 지금 다루지 않는다
`_data` 와 `_favorites` 를 연속 저장하다 두 번째가 실패하면 불일치가 남는다.
하지만 T-118(`isFavorite` 제거, `favoriteIds` 단일화)에서 구조적으로 사라진다.
지금 어댑터에서 트랜잭션을 흉내 내면 나중에 걷어내야 한다.

### T-009 착수 전 두 가지
| 항목 | 결정 | 이유 |
|---|---|---|
| `initializeData` try/catch | **T-009에 포함** | 어댑터가 throw하도록 만든 게 T-008. 받는 쪽을 안 만들면 T-009 끝난 시점에 지금보다 취약해진다 |
| 손상 데이터 복구 UI | **T-115로 미룸** | 실데이터 0건이라 복구할 게 없다. 내보내기가 아직 카테고리·메모를 빠뜨려(B3·B14) 고친 뒤가 순서 |

## 7. 검수 시점을 3회로 잡았다

매 단계 사람 검수는 비효율이다. 8단계 모두 같은 작업이라 두 번째부터 같은 얘기만 나온다.
매 단계는 md5 대조 + `node --check` + 브라우저 콘솔로 충분하다.

**사람 검수는 분기점에:**
1. 패턴이 확정된 직후 — "이 방식으로 N번 더 가도 되는가"
2. T-007 전체 완료 후 — 되돌리기 어려워지는 시점
3. P1 완료 후 — 보안·데이터 손실

실제로 1번에서 회귀 1건과 계획서 오류 2건이 나왔다.
검수 요청에 **"앞으로 반복할 때 문제 될 것"** 항목을 넣은 게 유효했다.

## 8. 문서 구조를 3분할했다

다른 세션에서 정한 방식을 이 프로젝트에도 적용.

| 경로 | 성격 | 작성 |
|---|---|---|
| `docs/devlog.md` | 기술 기록 — 어떻게 고쳤나, 함정, 원리 | Claude Code |
| `docs/worklog/날짜.md` | 그날 작업 | Claude Code |
| `docs/decisions/날짜.md` | 대화 판단 — 왜 그 길로 갔나 | **GON** |

**이유:** Claude Code는 코드와 커밋은 보지만 대화는 못 본다.
`prompts.chat` 를 왜 제외했는지, 실데이터 0건을 발견하고 계획을 어떻게 바꿨는지,
호이스팅 이해가 틀렸다가 정정된 과정 — 이런 건 자동으로 남지 않는다.

`worklog` 는 "무엇을 했나", `decisions` 는 "왜 그렇게 하기로 했나".
전자는 커밋 이력으로 재구성할 수 있지만, 후자는 대화에만 있다.
