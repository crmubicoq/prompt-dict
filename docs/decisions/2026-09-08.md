## 1. Codex 검수를 T-009 전에 넣기로 한 이유

## 2. T-009를 5단계로 쪼갠 이유

조사에서 위험이 한 곳에 몰려 있지 않다는 게 드러났다.

| 단계 | 성격 | 동작 변화 |
|---|---|---|
| T-009a | 어댑터 보강 | 없음 |
| T-009b | 읽기 경로 | 있음 (초기화 순서 재배치) |
| T-009c-1 | 안전한 진입점 7곳 | 있음 |
| T-009c-2 | 인라인 onclick 5곳 | 있음 |
| T-009c-3 | FileReader 콜백 + 초기화 저장 | 있음 |

**파일별이 아니라 위험도별로 나눴다.** 파일별로 나누면 `saveToLocalStorage`
를 반쯤 바꾼 상태가 생겨 어느 호출부가 어느 규약인지 섞인다.

## 3. 스냅샷 롤백 vs 호출부별 역연산

**스냅샷 일괄을 택했다.** 근거 셋:

1. 역연산은 호출부마다 다르고, 어려운 게 4곳이다
   (`deleteSelectedPrompts`, `handleFormSubmit` 수정, `deleteCategory`, `editCategory`).
   특히 `deleteCategory` 는 프롬프트별 원래 카테고리를 다 기억해야 한다.
   **되돌리기 코드 자체가 버그를 낳는 구간**이다
2. 19곳이 전부 같은 모양이면 읽기도 검수하기도 쉽다
3. 150개 300KB의 얕은 복사는 체감 비용이 없다

단, 얕은 복사는 요소 객체를 공유하므로 **제자리 변경은 못 되돌린다.**
그 3곳만 대상 객체 사본을 따로 잡거나 바뀐 객체를 모아 개별 복원했다.

## 7. 내 설계 실수 3건

기록해둘 가치가 있다. 셋 다 **"안전하게 만들려던 것이 오히려 위험을 만든"**
같은 형태다.

### 전역 가드 범위 과다 (F1)
"읽기 실패 시 저장 차단"을 설계하면서 **키 단위로 생각하지 않았다.**
검색 기록 5개가 깨졌다는 이유로 프롬프트·카테고리·즐겨찾기·테마 저장이
전부 막혔다. 게다가 원인이 사용자에게 안 보여 복구할 방법이 콘솔뿐이었다.

### 전역 핸들러가 롤백을 대신하지 못함 (F2 후속)
`unhandledrejection` 핸들러가 예외를 "처리"한다고 생각했는데,
**토스트만 띄우고 롤백은 건너뛴다.** 어댑터가 reject하면 호출부의
`!== true` 분기에 도달하지 못하기 때문이다.
결과적으로 실패했는데 메모리에 변경이 남고, 이후 다른 저장에 딸려 들어갔다.
파사드에서 rejection을 `false` 로 정규화해야 했다.

### `JSON.parse('null')` 미고려
읽기 규약을 "키 없음=null / 빈 배열=[] / 파싱실패=throw" 세 상태로 설계했는데,
`null` 이 **유효한 파싱 결과**라는 걸 놓쳤다. 저장소에 `"null"` 이 있으면
파싱은 성공하고 `null` 이 반환되어 "키 없음"으로 오인된다.

역설적으로 **검증 없던 기존 코드가 더 안전했다.** 예외가 나서 초기화가
중단되고 원본이 보존됐다. 추상화가 우연한 안전장치를 걷어낸 사례다.

## 8. 읽기와 쓰기의 실패 처리는 비대칭이 맞다

파사드에서 쓰기 rejection을 `false` 로 정규화하면서, 읽기도 대칭으로
맞추자는 생각이 들 수 있다.

**하지 않았다.** 읽기의 `throw` 는 T-009a에서 세운 보호의 핵심이다.
`null` 로 뭉개면 "손상"과 "키 없음"이 다시 섞여 F1 이전으로 돌아간다.

쓰기는 실패해도 롤백하면 되지만, 읽기는 실패를 뭉개는 순간
**잘못된 데이터로 앱이 계속 돌아간다.**

## 9. P1을 1-A(등록 마찰)부터 시작한 이유

1-B(보안·데이터)가 태스크는 더 많지만 뒤로 미뤘다.

- **보호할 데이터가 아직 없다.** XSS든 내보내기 누락이든 실데이터 0건이면
  위험이 이론적이다. 반대로 등록 마찰은 지금 당장의 병목이다
- **1-A가 끝나면 D1을 시작할 수 있다.** 데이터가 들어오면 1-B의 우선순위가
  실제 근거를 갖는다
- **P0가 데이터 손상 방어를 이미 깔아놨다.** 저장 실패 시 롤백, 손상 시
  키 단위 잠금, 원본 보관. 1-B가 늦어도 데이터가 날아가진 않는다

단, **T-116(UUID)만 예외로 먼저 했다.** 일괄 붙여넣기로 10개를 한 번에
넣으면 `Date.now()` 가 같은 밀리초에 겹친다. 일괄 등록의 전제 조건이다.

## 10. "미분류"를 "기타"와 합치지 않은 이유

기타를 재사용하면 코드가 줄어든다. 그래도 나눴다.

1. **기타는 사용자가 삭제·수정할 수 있는 일반 카테고리다.** 지우면 미분류
   프롬프트가 사이드바에서 통째로 사라진다
2. **의미가 다르다.** 기타 = 골라서 넣은 것, 미분류 = 아직 안 고른 것.
   합치면 T-105(일괄 분류)에서 **정리할 대상을 골라낼 수 없다.**
   150개 이관의 핵심이 바로 그 구분이다
3. 카테고리 삭제 시 소속 프롬프트가 기타로 가는 기존 동작과 충돌하지 않는다

구현: `categories` 배열 **밖의 특수 값**으로 두어 관리 화면에 나타나지 않게 했다.

## 11. 제목 자동 제안 — value 대신 placeholder

`value` 로 미리 채우면 직접 쓰려는 사용자가 **지우고 써야 해서 마찰이 는다.**
이 태스크의 목적과 반대다. 본문을 고칠 때마다 덮어쓸지도 애매해진다.

`placeholder` 는 사용자를 방해하지 않으면서 무엇이 저장될지 정확히 보여준다.

**역할 지정("너는 ~로서")도 패턴 감지 없이 그대로 제목으로 쓴다.**
감지해서 건너뛰면 동작이 예측 불가능해지고 정보량이 가장 많은 줄을 버릴
위험이 있다. 어차피 제안이고 사용자가 고친다. **규칙은 단순할수록 낫다.**

**수정 모드만 예외** — 고급 필드에 값이 있으면 자동으로 펼친다.
접혀 있으면 사용자가 기존 값을 못 본다.

## 13. T-101 결함이 준 교훈

T-101에서 카테고리 필수 검증을 해제하고 45/45 통과했으나,
`select` 의 `required` 속성이 남아 **실제 사용자는 여전히 카테고리를 골라야
했다.** 검증이 `dispatchEvent(new Event('submit'))` 을 써서 네이티브 폼 검증을
우회한 탓이다.

**검증은 통과했는데 기능은 안 고쳐진 상태였다.**

T-103을 하다가 우연히 발견했다. 안 했으면 D1에서 150개를 넣으려다
막혔을 것이다.

교훈: 테스트가 실제 진입 경로와 다른 경로를 타면 "코드가 바뀌었다"는
증명은 되지만 **"기능이 동작한다"는 증명은 안 된다.**
HTML 속성과 JS 검증이 이중으로 걸려 있으면 한쪽만 고쳐도 테스트는 통과한다.
